\begin{abstract}
Leaderboard scores for the same model on the same benchmark routinely disagree by
tens of points, yet the public record rarely says why. We assemble 46{,}559
evaluation records from 12 public sources (7{,}398 models, 1{,}954 benchmarks) into
one schema and audit what configuration information survives. In the
28{,}755-record, 10-source leaderboard subset, the fields that would explain
divergence are absent: prompt template and temperature have zero valid coverage,
and no leaderboard API we examined exposes the harness. Three case studies trace
how this missing metadata makes cross-source gaps uninterpretable, isolating three
mechanisms: a benchmark implemented differently by different harnesses (scoring
mode, parsing); multiple legitimate measurements under one name (n-shot, language
scope, judge); and apparent independent agreement that is one pipeline reported
twice. A controlled factorial experiment quantifies the effects: prompt format
alone drives 27\% of GSM8K variance, temperature under 1\%. We adapt the open EEE
schema into EvalSpec, requiring the fields whose absence breaks comparison, and
release it with the dataset so future evaluations report extractable, comparable
configurations.
\end{abstract}

Open LLM Leaderboard v2 (OLv2) reports Gemma-7B's Big-Bench Hard (BBH) score as
21.12; the Jamba, RecurrentGemma, and MAmmoTH2 papers, among others, report BBH
between 55 and 60 for the same model, a gap over 35 points. Neither side
fabricates: each reports the score its pipeline produced. What is missing is the
procedure: OLv2 runs BBH with lighteval log-likelihood scoring, whereas the papers
use the original 3-shot chain-of-thought protocol. These are not the same
measurement, and a benchmark name does not make them so. The same pattern recurs
for Gemma-2-9B (\S\ref{sec:sealion}), where the metadata that would distinguish
the two protocols is stripped from every record before the scores meet.

This example is the rule, not the exception: evaluation results pass through a
chain of hands, a model author runs an internal sweep, a leaderboard
re-evaluates the checkpoint, an aggregator scrapes the leaderboard, a downstream
paper cites the aggregator, and at each stage information about how the score was
produced is lost or quietly reinterpreted, until two scores meeting on a
comparison table share nothing but a benchmark name. We therefore assemble
46{,}559 records from 12 sources (7{,}398 models, 1{,}954 benchmarks) and, for the
10-source 28{,}755-record leaderboard subset, ask what configuration survives. The
fields that most determine how a score is produced (harness, scoring mode, prompt
template, n-shot) are the ones the subset records least: prompt template has zero
coverage, and none of the leaderboard APIs we examined expose the harness.
Temperature is also absent, but a factorial experiment (\S\ref{sec:cases}) shows
it drives under 1\% of variance, so its zero coverage costs comparability little;
the high-impact fields above do the damage. We then diagnose cases where the same
model received sharply different scores on the same benchmark.

The case studies are the contribution; the extraction pipeline is the instrument
that found them. Each isolates a mechanism by which scores become incomparable
without either source erring: implementation choices the benchmark leaves
underspecified, multiple legitimate measurements under one name, and apparent
independent evidence sharing a single pipeline. This is an audit-grounded position
paper, dataset as instrument, mechanisms as evidence, EvalSpec as remedy.

\textbf{Contributions.}
\begin{itemize}
    \item A cross-source audit of metadata coverage in the public evaluation ecosystem.
    \item Three case studies of cross-source score divergence, diagnosed end-to-end.
    \item EvalSpec, an adaptation of the EEE schema requiring the fields whose
      absence the audit shows to break comparison.
    \item Public release of the dataset (46{,}559 records) and the EvalSpec schema
      under CC-BY-4.0, built on the EvalEval EEE schema
      \citep{evaleval2026everyevalever} so future evaluation papers report
      extractable scores and the community can adopt and extend it.
\end{itemize}

Several studies show benchmark scores are sensitive to implementation choices the
public record rarely exposes: \citet{alzahrani2024} report MMLU gaps up to fifteen
points from harness choice alone; \citet{biderman2024} extend this to prompt
format, tokenisation, and generation configuration; \citet{singh2025} document
score instability on Chatbot Arena under different aliases; and data contamination
\citep{sainz2023} is a parallel threat whose detection also needs richer per-run
records. These establish \emph{that} scores vary with protocol; we trace the
concrete mechanisms by which that variation enters the cross-source record, and
which specific absences produce which gaps.

A separate line proposes structured documentation. Model Cards \citep{mitchell2019}
and Datasheets \citep{gebru2021} set the norm for models and data; three concurrent
2025 proposals, BenchmarkCards \citep{sokol2025}, EvalCards \citep{dhar2025}, and
Eval Factsheets \citep{bordes2025}, extend it to evaluation. These are
prescriptive and narrative; EvalSpec (\S\ref{sec:evalspec}) differs on the two axes
that decide whether a specification changes practice: it is \emph{machine-validated}
(records checked by SHACL shape constraints, not prose) and \emph{audit-grounded}
(fields chosen because their absence demonstrably breaks comparisons,
\S\ref{sec:cases}). Holistic harnesses like HELM \citep{liang2023helm} record rich
metadata, but only for their own runs; EvalSpec instead targets cross-source
interchange. General reproducibility checklists
\citep{pineau2021reproducibility} are hand-filled prose; EvalSpec makes conformance
a property of the record, e.g.\ a SHACL shape requiring \texttt{judge\_model}
whenever \texttt{scoring\_mode} is \texttt{preference} mechanically rejects an
LLM-judge score that omits the judge (\S\ref{sec:truthfulqa},
Appendix~\ref{app:exp-judge}). EvalSpec is designed to sit on existing
reproducibility infrastructure rather than replace it: it adopts EEE as its
cross-source interchange substrate and Croissant-style dataset/task versioning
(commit hashes, checksums) for benchmark snapshots, aligning evaluation records
with emerging dataset-metadata standards rather than introducing a parallel one.


\subsection{The EEE Schema}

%% DRAFT --------------------------------------------------------------
% Our analysis builds on the Every Eval Ever (EEE) schema, a unified
% JSON format for storing evaluation records from heterogeneous sources.
% Each record captures one model's result on one benchmark from one
% source, organised into four blocks: \texttt{model\_info} describes
% the model under evaluation; \texttt{eval\_library} describes the
% harness used to produce the score; \texttt{source\_metadata} describes
% the source of the record and its provenance; and
% \texttt{evaluation\_results} contains the score itself along with
% per-run generation configuration. Table~\ref{tab:eee-fields} lists the
% fields most relevant to this paper.
%
% A unified schema is the right abstraction for cross-source comparison
% because the alternative --- comparing scores across sources whose
% formats and conventions differ --- requires implicit alignment that
% nobody verifies. The schema makes the alignment explicit and turns
% missing information from an invisible gap into a recordable absence:
% a field that no source populates is visibly empty in every record,
% rather than silently inferred away.
%% END DRAFT ----------------------------------------------------------

This paper is built on, and extends, the open Every Eval Ever (EEE) schema
released by the EvalEval Coalition
\citep{evaleval2026everyevalever}, which articulates the
cross-framework score-comparability problem this paper investigates (citing the
gap between HELM~\citep{liang2023helm} and EleutherAI's
lm-evaluation-harness~\citep{gao2024lmevalharness} on LLaMA~65B MMLU, 0.637
vs.\ 0.488); our case studies trace the specific mechanisms behind such gaps in
the public record.
EEE is a unified JSON format storing one model's result on one benchmark from one
source, with four objects: \texttt{model\_info} (model name, id, developer),
\texttt{eval\_library} (harness name and version), \texttt{source\_metadata}
(source, type, evaluator relationship), and \texttt{evaluation\_results} (metric
and score, with an optional \texttt{generation\_config} for temperature and prompt
template). A unified schema turns missing information from an invisible gap into a
recordable absence, a field no source populates is empty in every record rather
than silently inferred, and those visibly-empty fields motivate this paper. We
adapt EvalSpec (\S\ref{sec:evalspec}) from EEE and release the dataset and schema
under CC-BY-4.0 for the community to extend.

\subsection{How We Gathered the Data}
\label{sec:pipeline}

%% DRAFT --------------------------------------------------------------
% We ingest evaluation records from eleven public sources: eight
% leaderboards (Open LLM Leaderboard v2, AlpacaEval 2, Chatbot Arena,
% BigCodeBench, EvalPlus, BFCL, SWE-Bench, WildBench, MT-Bench), the
% HuggingFace model-card YAML model-index, and Papers With Code. Each
% source is handled by a dedicated converter that maps its native
% format onto the EEE schema; records that fail JSON-schema validation
% are dropped, and duplicates are deduplicated on the composite key
% \texttt{(model\_id, benchmark, source)}.
%
% The pipeline is not uniform in how much it trusts each source. We
% distinguish three levels.
%
% \paragraph{Deterministic.} Schema validation and ID normalisation are
% rule-based and do not depend on any heuristic. Model identifiers are
% lowercased; \texttt{-hf} suffixes and shot annotations are stripped;
% benchmark names are normalised to a canonical form. These operations
% are reversible and produce no false positives.
%
% \paragraph{Regex-based and fragile.} Papers With Code does not expose
% a structured API; results are scraped from HTML tables whose layout
% varies by paper. Score values, model identifiers, and benchmark names
% are extracted by regex. We treat this layer as the least reliable
% part of the pipeline and audit it explicitly in
% Section~\ref{sec:pwc-audit}.
%
% \paragraph{External knowledge.} Several sources do not expose the
% harness they use in their data, but the harness is known from
% platform documentation (for example, OLv2 uses lighteval; AlpacaEval
% uses alpaca\_eval). We record these inferred values in a separate
% \texttt{inferred\_harness} field rather than in
% \texttt{eval\_library.name}, so that self-reported and inferred
% values remain distinguishable downstream.
%
% Cross-source collisions are detected after normalisation: records are
% grouped by \texttt{(model\_id, benchmark)}, and every pair of records
% from distinct sources within a group is emitted as a collision pair
% with its score delta and metadata-match annotations. The full
% procedure is described in Appendix~\ref{app:collision}.
%
% We deliberately abstain from two operations that would otherwise be
% tempting. We do not use a language model to re-extract scores from
% paper PDFs or HTML, because doing so would introduce a second layer of
% errors that we could not separate from the errors already present in
% the sources. We do not manually correct individual records, because
% the audit's value depends on reporting what the public ecosystem
% actually contains, not what it would contain after curation.
%% END DRAFT ----------------------------------------------------------
The dataset is assembled from three source classes. Leaderboards are taken as
authoritative: each fetcher downloads at runtime and emits a schema-conformant
record per model$\times$benchmark cell, with n-shot and chain-of-thought from the
fixed protocol; OLv2 exposes only model ids, scores, and a submission date, no
harness, prompt template, scoring mode, or temperature. HuggingFace Model Cards
are parsed from the YAML \texttt{model-index}. The third source is ArXiv
extraction: an LLM (Claude Haiku via OpenRouter) reads paper prose into the EEE
schema for 100 papers, returning per-benchmark metadata (n-shot, temperature,
prompt template, chain-of-thought, harness) when explicitly stated; it may
hallucinate, so we treat these fields as unverified at scale.

\section{Quantitative Analysis}
\label{sec:quant}

\subsection{Human Annotation of Automatic Score Extractions}
\label{sec:score-ann}

\paragraph{Score extraction precision and recall.}
We audited 2{,}027 extracted (model, benchmark, score) entries against the source
papers across 10 ArXiv papers (listed in Table~\ref{tab:score-ann-app},
Appendix~\ref{app:audit}). \emph{Precision}, extracted scores that match the
paper, is \textbf{97.5\%} (1{,}977/2{,}027); the 50 errors are systematic
artefacts (base/chat variant duplication, 33; a spurious HumanEval leading ``0'',
8; a Qwen1.5-32B-as-34B mislabel, 5; duplicate Elo attribution, 3; one wrong
pass@k, 1). \emph{Recall}, reported scores the pipeline captured, is
approximately \textbf{81\%} but variable (52--100\% per paper): it captures
headline tables but skips secondary ones and, in table-heavy papers, whole
comparison models. Neither check verifies the surrounding metadata. Separately,
16{,}374/17{,}228 (95.0\%) LLM-extracted ArXiv records carry a non-null
score, a structural presence check, not a correctness one.

\subsection{Human Annotation of Automatic Harness Identification}
\label{sec:harness-ann}
We assembled two balanced samples from the ArXiv source: five papers that name a
harness (\emph{with-harness}: BLOOM, Llemma, Sheared LLaMA, Aya 23, Nemotron-4
15B) and five that do not (\emph{without-harness}: Code Llama, Mamba, Reka, Jamba,
a Llama-2 survey), covering 817 and 869 harness-call rows. Each row's
\texttt{eval\_library.name} was verified against the source text under a strict
rubric (canonical equivalents accepted, a paper's distinctly-named fork required
verbatim; Appendix~\ref{app:harness}).

Per-row precision on the with-harness sample is 712/817 = 87.1\%: three papers
reach 100\% (BLOOM 436/436, with the \emph{Prompted Language Model Evaluation
Harness} fork correctly extracted, plus Sheared LLaMA and Aya 23), while two
expose a failure mode, when a harness is attributed to a broad group (``across
all aforementioned tasks'', Nemotron-4 15B, 6/96; ``for open access models'',
Llemma, 74/89), the LLM tags only the benchmarks named in the same sentence.
Abstention on the without-harness sample is 869/869 = 100\%: \texttt{unknown} for
every row, and text search confirms none names a public harness for its own
evaluations.

\label{sec:discrepancies}

\paragraph{Metadata coverage.}
Figure~\ref{fig:coverage} reports coverage for five configuration fields over the
full 46{,}559-record dataset and the 10-source 28{,}755-record leaderboard subset,
counting a field as populated whenever the record carries a non-``unknown''
value, from the source API, pipeline-attached from documentation, or
LLM-extracted.

The headline is that the fields most responsible for divergence are either absent
from the subset (\texttt{prompt\_template} and \texttt{temperature} at 0\%) or
present only because the pipeline attaches \texttt{lm\_eval} to every OLv2 record
from documentation (\S\ref{sec:pipeline}): no leaderboard we examined returns
harness identity via its API, so the 93\% subset harness coverage is
auto-attachment, not source data. As \S\ref{sec:bbh} shows, OLv2 actually runs
\emph{lighteval}, so even the pipeline-attached \texttt{lm\_eval} label is itself
inferred.

\paragraph{One platform plus a sparse tail.}
OLv2 supplies 26{,}790 of the 28{,}755 leaderboard records (93.2\%), so the subset
figures largely measure one platform's API. Ablating it sharpens the finding
rather than weakening it (Table~\ref{tab:coverage-app}, final column): across the
remaining nine sources (1{,}965 records) n-shot coverage falls to 71.0\% and
\texttt{harness}, \texttt{prompt\_template}, \texttt{temperature}, and
\texttt{chain\_of\_thought} are all 0.0\%, the tail exposes nothing beyond the
protocol-fixed n-shot count, and the subset's apparent harness and CoT coverage is
OLv2's pipeline-attached values alone.

\paragraph{Scoring mode is unmeasurable.}
\texttt{scoring\_mode}, the field the case studies show most consequential, is
absent from the audit because no source records it discretely; it is implicit in
the harness configuration. Unlike harness identity it cannot even be
pipeline-attached, since one platform runs the same benchmark in either mode
(\S\ref{sec:bbh}). That unmeasurability is itself the argument for making it a
first-class required field (\S\ref{sec:evalspec}).

\section{Case Studies}
\label{sec:cases}

The case studies fall into three groups, one per mechanism by which scores
become incomparable across sources; Figure~\ref{fig:casestudies-unified} shows a
representative divergence for each. A controlled factorial experiment first
quantifies the factors (four models $\times$ three benchmarks $\times$ three
prompt formats $\times$ two temperatures $\times$ two n-shot counts; 306
evaluations; Appendix~\ref{app:exp-grid}). Prompt format dominates: on GSM8K it
accounts for ${\approx}27\%$ of 5-shot variance ($F = 13.0$, $p < 0.001$; 95\%
bootstrap CI $[14.1\%, 44.8\%]$), with MMLU ($\eta^2 \approx 24.5\%$) and a GPQA
run ($\eta^2 \approx 13.8\%$) consistent but underpowered ($p = 0.43$, $0.51$).
Temperature contributes under 1\% ($\eta^2 = 0.25\%$), and the n-shot effect is
benchmark-dependent: negligible on MMLU but on GSM8K inseparable from the parser,
since 0-shot runs collapse when models omit the expected delimiter. The grid shows
these factors move scores systematically and by how much; the case studies below
show the same factors in the wild, each isolating one mechanism by which two
separately published scores under a shared name measure different things.

\subsection{Case Study 1: Undocumented Scoring Mode and Parsing}
\label{sec:protocol}

Here the harness makes implementation choices the benchmark specification leaves
open, and different choices produce measurements that cannot be compared on the
same scale even when both are correctly executed.

\paragraph{BBH: log-likelihood vs.\ chain-of-thought.}\label{sec:bbh}
BBH \citep{suzgun2023} specifies 3-shot chain-of-thought generation, with the
answer extracted from free-form reasoning, the protocol ArXiv papers follow.
OLv2 instead runs BBH under \emph{lighteval} with log-likelihood scoring (the
model ranks candidate answers by token probability; no text is generated). OLv2's
API exposes no harness field, so \emph{lighteval} and its scoring mode are known
only from platform documentation. The effect is visible in the data
(Table~\ref{tab:bbh-app}, Appendix~\ref{app:casetables}): Gemma-7B scores 21.12
on OLv2 against 55.10--59.60 in ArXiv papers,\footnote{The 59.60 figure is
reported under the surface label ``BigBench-Hard''; our normaliser keys on the
``BBH'' alias, so it is shown for completeness but held out of the automated
collision counts.} a gap over 35 points; the same holds for Gemma-2-2B (11.76
vs.\ 40.80) and MAmmoTH2-7B-Plus (18.93 vs.\ 63.10). This is not a generic
scoring-mode effect: E2 (Appendix~\ref{app:exp-e2}) shows the
log-likelihood-vs-generation gap on MMLU is at most 0.28\,pp, two orders of
magnitude smaller, so the BBH gap is specific to lighteval log-likelihood
meeting BBH's CoT structure.

\paragraph{MATH Lvl 5: a silent answer-parser swap.}\label{sec:math}
OLv2 scored MATH Level 5 (1{,}324 problems, 5-shot) with a SymPy parser; in
February 2025 HuggingFace replaced it with Math-Verify and re-evaluated all
models \citep{kydlicek2025mathverify}. The old parser mishandled
\textbackslash{}boxed\{\} outputs, sets/matrices/intervals, and
numerical-equivalence (e.g.\ $1/3$ vs.\ $0.333\ldots$); the swap raised scores
by $+4.66$\,pp on average over 3{,}751 models ($+8.27$ Algebra, $+6.93$
Prealgebra, up to ${\approx}90$ points individually). OLv2 records a submission
date but no evaluation timestamp, so pre- and post-transition scores cannot be
told apart from the record, a model submitted in 2024 now carries a
post-transition score.

\paragraph{GSM8K: prompt format breaks the parser.}\label{sec:gsm8k}
The same parser sensitivity arises whenever a format-specific extractor meets a
prompt-shaped output. In the factorial grid, Qwen2.5-14B-Instruct on GSM8K
(5-shot, lm-evaluation-harness 0.4.11, temperature~0) scores 58.5\% (plain),
57.0\% (instruct), and 2.5\% (cot) (E1, Appendix~\ref{app:exp-e1};
Figure~\ref{fig:case1-parser}). The $\approx$56-point CoT collapse is parser
failure: the harness extracts the answer with the GSM8K delimiter
(\texttt{\#\#\#\#~\{answer\}}), which CoT prose omits, so the regex records zero
even though the reasoning is correct. As with Math-Verify, the score reflects
the parser's format assumptions, not capability: a CoT-prompted GSM8K score and
a plain-prompted one are incommensurable under one label.

\subsection{Case Study 2: One Name, Several Specifications}
\label{sec:onenametwo}

Unlike Case Study~1 (\S\ref{sec:protocol}), where one benchmark specification is
implemented differently by different harnesses, here several legitimate
specifications coexist under one benchmark name, so two equally-labelled scores
can measure genuinely different things. Each example below states the gap, the
two source configurations, and the missing field that would explain it.

\paragraph{TruthfulQA: n-shot and judge confounded.}\label{sec:truthfulqa}
Llama-2-Chat-7B is recorded at 57.04 and 26.30, both labelled ``TruthfulQA''
\citep{lin2022truthfulqa}; both use the generation-based metric (\% truthful and
informative), not MC1/MC2. The 57.04 is from the Code Llama paper
\citep{roziere2023codellama} (6-shot, InstructGPT-format prompt, GPT-3 judge);
the 26.30 figures use the T\"ulu suite \citep{ivison2023camels}, e.g.\ the OLMo
paper \citep{groeneveld2024olmo} (0-shot, a fine-tuned Llama-2-7B judge). The
30-point gap therefore confounds shot count (6 vs.\ 0) and judge (GPT-3 vs.\ a
fine-tuned Llama-2-7B), and neither record carries an \texttt{n\_shot} or judge
field. A controlled experiment (Appendix~\ref{app:exp-judge}) isolates the
judge: over fixed responses, varying only the judge shifts means by up to
1.35/10 and can reverse two systems' ranking, so judge identity alone makes two
``TruthfulQA'' scores incomparable.

\paragraph{Belebele: n-shot and language scope confounded.}\label{sec:belebele}
Mistral-7B is recorded at 32.80 and 79.42, both ``Belebele''
\citep{bandarkar2023belebele}. The 32.80 is the Reka report
\citep{team2024reka} (0-shot, multilingual average over 150 variants); the 79.42
is Falcon2 \citep{malartic2024falcon2} (5-shot, English only). Falcon2's own
0-shot English score for Mistral-7B, 32.48, nearly matches Reka's 32.80, which
isolates the effect: 0-shot$\to$5-shot on English yields the full 47-point gain
($32.48 \to 79.42$) while language scope alone contributes almost nothing. The
46.6-point gap is driven by n-shot, not language scope, and neither record
labels either dimension.

\paragraph{HellaSwag: scoring mode and n-shot confounded.}\label{sec:hellaswag}
Gemma-7B is recorded at 49.80 and 81.20, both ``HellaSwag''
\citep{zellers2019hellaswag}. The 49.80 is the Phi-3 report
\citep{abdin2024phi3} (5-shot, generation-based, temperature~0); the 81.20 is
the Gemma report \citep{gemmateam2024gemma} (0-shot, log-likelihood over the
four continuations). The $\approx$31-point gap is too large for shot count
alone, on a log-likelihood benchmark n-shot moves scores a few points (our
grid: MMLU 0-vs-5-shot differ 2.6\,pp, $\eta^2\approx1\%$,
Appendix~\ref{app:exp-grid}). The driver is scoring mode: free-form generation
of the continuation is structurally harder than ranking pre-specified
continuations. Neither record labels scoring mode or n-shot, so the gap is
indistinguishable from a capability difference (Appendix~\ref{app:hellaswag}
gives an alternative rendering of Figure~\ref{fig:casestudies-unified}).

\subsection{Case Study 3: Shared Pipelines Fake Independence}
\label{sec:convergence}\label{sec:sealion}

Two sources reporting the same score to several decimals need not be independent
measurements; one may be the other re-reported. OLv2 reports Gemma-2-9B's BBH
score as 34.10, and the SEA-LION paper (\citealt{ng2025sealion};
arXiv:2504.05747) reports the same model at 34.10, an exact two-decimal
match, while listing Open LLM Leaderboard among its benchmark sources. Such a
match is consistent with either direct importation of the OLv2 score or
independent re-evaluation on identical (lighteval) infrastructure, and the EEE
record cannot distinguish them; but our harness-version control
(Appendix~\ref{app:exp-e3}) shows independent reruns vary by up to 1.3\,pp across
seeds, so an exact match is far more consistent with a re-import than a re-run,
which would almost never agree to the second decimal. Either way the two records
share a pipeline origin. The fields that would separate replication from
re-import (\texttt{harness}, \texttt{prompt\_template\_hash},
\texttt{evaluation\_timestamp}) were dropped before the comparison table, leaving
the match as the only signal.

The Gemma 2 and Gemma 3 reports instead list 68.20, 69.00, and 69.40, using
chain-of-thought generation rather than OLv2's 3-shot lighteval log-likelihood,
which explains the $\approx$35-point gap (the harness mismatch of
\S\ref{sec:bbh} compounding here). All five sources are in
Table~\ref{tab:sealion-app} (Appendix~\ref{app:casetables}).

\subsection{The Misunderstanding Chain}

%% DRAFT --------------------------------------------------------------
% The findings of the audit and the case studies share a common shape.
% An evaluation result is produced by a long chain of decisions:
% which harness, which version, which prompt template, which n-shot
% count, which temperature, which scoring mode, which answer extractor.
% At evaluation time, every link in the chain is known: the runtime
% environment carries the harness version, the prompt template is a
% string in memory, the temperature is a float. Between evaluation
% time and the reader, almost all of this information is dropped.
% Leaderboard APIs return scores and model identifiers but rarely
% expose the configuration that produced them. Aggregators store
% whatever the APIs return. Downstream papers cite the aggregator.
% By the time two scores meet on a leaderboard page, the procedures
% behind them are no longer comparable in any verifiable way.
%
% Two alternatives to recording the configuration are sometimes
% suggested. The first is independent re-evaluation: if scores
% diverge, run the evaluation again under known conditions.
% Section~\ref{sec:results-discrepancies} shows that this is not
% available at scale. The model--benchmark overlap between sources is
% too sparse for cross-source verification to arise naturally, and
% targeted re-evaluation across thousands of models is not realistic.
% The second is automatic re-extraction from public artefacts. The
% Papers With Code artefact rate (57\% of raw records removed in our
% pipeline) shows that automatic ingestion of unstructured sources
% produces a substantial fraction of semantically wrong but
% schema-valid records, and the harness-identification audit
% (Section~\ref{sec:harness-audit}, pending) is expected to show that
% even relatively explicit information is hard to recover reliably.
%
% This leaves documentation. The argument is not that documentation is
% sufficient --- one can imagine adversarial cases where it is not ---
% but that in the current ecosystem it is necessary, because the two
% alternatives have failed. The closest analogy is the move to
% pre-registered clinical trials: when independent replication of every
% trial is infeasible, mandatory protocol recording becomes the
% substitute. Evaluation reporting is in a similar position, and
% requires a similar response.
%% END DRAFT ----------------------------------------------------------
An evaluation result is the product of a long chain of decisions (harness,
version, prompt template, n-shot, temperature, scoring mode, answer
extractor), each known at evaluation time but almost all dropped before the
reader. The three case studies locate the loss: at the leaderboard
(\S\ref{sec:protocol}), at the benchmark label (\S\ref{sec:onenametwo}), and at
the appearance of independent measurement (\S\ref{sec:convergence}). The two
alternatives to documentation both fail where the need is greatest: re-extraction
cannot recover what the leaderboard subset never records
(Figure~\ref{fig:coverage}), and re-evaluation does not scale across thousands of
model--benchmark pairs. This leaves documentation, necessary, if not always
sufficient.

\subsection{EvalSpec: Adapting EEE for Comparable Reporting}
\label{sec:evalspec}

%% DRAFT --------------------------------------------------------------
% EvalSpec is a machine-readable reporting specification for
% evaluation runs. It is designed to be the smallest set of fields that
% turns a score into an identifiable measurement: enough that two
% records meeting on the same benchmark can be compared without an
% intervening act of guesswork.
%
% Field selection follows from the audit. The Required tier
% (EvalSpec-R) contains the fields whose absence makes attribution
% impossible: model identifier, benchmark identifier, scoring mode
% (one of log-likelihood, generation, preference, execution), harness
% name and version, n-shot count, date, and random seed. The
% Recommended tier (EvalSpec-Rec) contains the fields whose absence
% makes attribution incomplete: prompt-template hash, temperature,
% top-p, quantisation, hardware, software environment. The Full tier
% (EvalSpec-F) contains the fields needed for full reproducibility:
% provenance link, contamination check, compute hours.
% Table~\ref{tab:evalspec-fields} lists the full set.
%
% EvalSpec is encoded as a JSON-LD vocabulary extending schema.org
% and compatible with Croissant metadata records. Compliance is
% enforced by SHACL shape constraints, so that a record can be
% mechanically checked against any tier. The prompt template is
% recorded as a SHA-256 hash of the canonical template string, which
% keeps the specification zero-overhead while preserving the ability
% to detect template changes across runs. A reference validator and
% the full vocabulary are released alongside the dataset.
%
% None of the Required fields require new instrumentation. Temperature
% is one float per run; the prompt template is one hash; the harness
% name and version are strings already present in the runtime
% environment. The barrier to adoption is not implementation cost but
% API exposure: the leaderboards already know these values, but their
% APIs do not return them.
%% END DRAFT ----------------------------------------------------------

EvalSpec adapts the open EEE schema (\S\ref{sec:related}) to the gaps this audit
exposes: starting from EEE, it requires the configuration fields whose absence the
case studies show to break cross-source comparison, so two records on the same
benchmark can be compared without guessing the procedure behind them. We release
it with the populated dataset not as a finished standard but as a starting point,
so that future evaluation papers report the configuration that makes their scores
easy to extract and compare, and the community can keep adapting and extending it.

Field selection follows from the case studies (\S\ref{sec:cases}):
\texttt{scoring\_mode} from the BBH and HellaSwag collapses
(\S\S\ref{sec:bbh},~\ref{sec:hellaswag}); \texttt{harness\_name} and
\texttt{harness\_version} from SEA-LION (\S\ref{sec:sealion}), where harness
identity separates independent measurement from a shared-pipeline artefact;
\texttt{n\_shot} and \texttt{benchmark\_variant} from TruthfulQA, Belebele, and
HellaSwag (\S\S\ref{sec:truthfulqa}--\ref{sec:hellaswag}), where shot count and
metric variant shift the regime unlabelled; \texttt{judge\_model} from TruthfulQA,
where varying only the judge moves means up to 1.35/10 and reorders rankings
(cross-judge correlations $+1.0$ to $-0.3$; Appendix~\ref{app:exp-judge}); and
\texttt{evaluation\_timestamp} from the Math-Verify swap (\S\ref{sec:math}), which
changes scores silently under one label. Two Recommended fields follow the same
logic: \texttt{judge\_prompt\_hash} (the rating depends on the judge prompt and
rubric, not the model alone) and \texttt{answer\_parser\_version} (the Math-Verify
parser swap is invisible to \texttt{harness\_version}); hashed fields are
canonicalised before hashing so cosmetic differences do not cause spurious
mismatches. The full set by tier is in Table~\ref{tab:evalspec-fields-app}
(Appendix~\ref{app:evalspec}).

Instantiating these fields for the SEA-LION collision
(Table~\ref{tab:evalspec-worked}, Figure~\ref{fig:evalspec-json},
Appendix~\ref{app:evalspec}) shows two suffice: \texttt{scoring\_mode} splits the
34.10 log-likelihood pair from the 68--69 generation reports, and
\texttt{harness\_name} plus \texttt{evaluation\_timestamp} separate SEA-LION's
re-import from an independent re-run. In the actual records all are
\texttt{unknown}, which is why the collision is unresolvable and recording them
the resolution.

EvalSpec is encoded as a JSON-LD vocabulary (extending \texttt{schema.org},
compatible with Croissant) whose tiers can be mechanically checked by SHACL shape
constraints, so conformance needs no human judgement; the prompt template is
stored as a hash of its canonical string. None of the required fields need new
instrumentation, the values already exist at evaluation time; the barrier is API
exposure, not implementation cost.


\subsection{Recommendations}

%

\paragraph{For practitioners.}
\emph{Leaderboard operators} should expose \texttt{harness\_name},
\texttt{harness\_version}, \texttt{scoring\_mode}, and
\texttt{evaluation\_timestamp}, known at evaluation time, so a logging decision,
not an engineering project; SEA-LION (\S\ref{sec:sealion}) shows the cost, where an
exact match becomes unreliable evidence of replication. \emph{Model developers}
should ship at least one EvalSpec-R record per reported benchmark, making scores
verifiable against later third-party evaluations (E1, Appendix~\ref{app:exp-e1}:
58.5\% vs.\ 2.5\% from one unrecorded prompt format). \emph{Schema designers}
should treat \texttt{scoring\_mode} as a first-class controlled-vocabulary field
(\texttt{log-likelihood}, \texttt{generation}, \texttt{preference},
\texttt{execution}), since no combination of harness, n-shot, and timestamp
recovers the log-likelihood-vs.-generation boundary (BBH, \S\ref{sec:bbh}; E2,
Appendix~\ref{app:exp-e2}, shows the converse: under 0.3\,pp when scoring mode
alone varies).

\paragraph{Adoption.}
None of the Required fields needs new instrumentation, they already exist at
evaluation time, so the barrier is incentive, not engineering: a producer emits
them by logging and a leaderboard by adding them to its API response. Even partial
uptake pays off. Because conformance is machine-checkable (SHACL), records can be
validated automatically rather than by hand; because the fields are uniform across
sources, incomparable protocols stop being silently averaged into ``SOTA''
comparisons and cross-source meta-analysis becomes possible. The cheapest
migration path is producer-side: model developers who ship one EvalSpec-R record
per reported benchmark make their own scores verifiable, which in turn pressures
aggregators and leaderboards to surface the same fields.

\section{Conclusions}

Public evaluation records routinely report a score without the procedure that
produced it. Across 46{,}559 records from 12 sources, the configuration fields
most responsible for score divergence (harness identity, scoring mode, prompt
template) are largely absent from the leaderboard subset, where prompt template
and temperature reach zero valid coverage and no API exposes the evaluation
harness. The cross-source overlap that would allow independent verification is
rare and concentrated in a single dominant source. Three case studies show how
these absences turn ordinary score gaps into uninterpretable ones, and a
controlled factorial experiment confirms that an undocumented prompt-format or
answer-parser choice can move a score by tens of points on the same model,
benchmark, and harness. Because targeted re-evaluation does not scale and
automatic re-extraction cannot recover what a source never recorded,
documentation is the remaining identification strategy. EvalSpec specifies
the minimum set of fields to record, grounded in the audit and validated against
the case studies. The dataset, schema, and pipeline are released for the
community to extend.

\section*{Limitations}

\paragraph{Source concentration.} The leaderboard subset is dominated by Open
LLM Leaderboard v2, which contributes 26{,}790 of 28{,}755 records (93\%).
Aggregate coverage statistics therefore largely describe OLv2 plus a long tail
of much smaller sources; statements about ``the leaderboard ecosystem'' should
be read as statements about one dominant platform and a sparse periphery, not a
balanced cross-section. We report the leaderboard subset separately from the
full dataset throughout for this reason, and ablate OLv2 directly
(Table~\ref{tab:coverage-app}): with it removed, the nine-source tail carries
0.0\% coverage on harness, prompt template, temperature, and chain-of-thought,
and only the protocol-fixed n-shot count (71.0\%) survives, so the dominant-source
caveat does not overturn the headline, it sharpens it.

\paragraph{Single-extractor ArXiv pipeline.} The ArXiv source is produced by a
single LLM extractor (Claude Haiku). Our audits (\S\ref{sec:score-ann},
\S\ref{sec:harness-ann}) verify its output against the source papers on a
20-paper sample by hand, but we did not collect inter-annotator agreement at
scale or compare independent extractors, so the reported precision and recall
are point estimates on a small sample rather than ecosystem-wide guarantees. We
accordingly exclude the ArXiv source from the headline coverage analysis and
treat its metadata as unverified at scale.

\paragraph{Existence, not prevalence.} The three case studies are hand-selected
instances of cross-source divergence, chosen because their mechanisms are
diagnosable. They establish that each mechanism occurs and is consequential;
they are not a random sample. We therefore do not claim how frequently
scoring-mode mismatch, variant conflation, or shared-pipeline reuse arise across
the ecosystem. Quantifying that prevalence over all cross-source collisions is
left to future work; the collision-detection pipeline that surfaced these cases
could in principle support such a census.

\paragraph{Statistical power.} The factorial grid is adequately powered on GSM8K
(prompt format $F=13.0$, $p<0.001$) but underpowered on MMLU ($F=0.98$,
$p=0.43$) and GPQA ($F=0.72$, $p=0.51$), both reduced to single-seed or
single-temperature designs under compute limits. We report the MMLU and GPQA
results as directionally consistent with the GSM8K pattern, not as independent
confirmation, and rest the load-bearing claims on GSM8K. Several grid cells use
a 200-problem subset (\texttt{limit=200}) rather than the full benchmark; a
full-set rerun of one cell confirms the subset is representative to within
1.3\,pp (Appendix~\ref{app:exp-grid}). Our temperature result, under 1\% of
variance, is established on GSM8K under greedy generation with answer parsing;
it should not be read as a universal claim, and open-ended generation or
safety/refusal tasks, where sampling drives output diversity, may show larger
temperature sensitivity. The same \texttt{hf}-vs-vLLM backend shift
(Appendix~\ref{app:exp-grid}) is a further reason to treat the absolute
prompt-format and temperature magnitudes as backend-conditional.

\paragraph{Pipeline-attached harness labels.} The 93\% harness coverage in the
leaderboard subset is attached by our pipeline from platform documentation, not
returned by any source API. It records what a platform documents it runs, which
can itself drift from the runtime, OLv2 is documented as \texttt{lm\_eval} but
actually runs \emph{lighteval} (\S\ref{sec:bbh}). The released dataset marks every
such value as inferred (not source-reported) so downstream users can correct or
discount it rather than propagate the documentation label as ground truth.

\paragraph{Extending the schema.} EvalSpec is released as an extensible adaptation
of EEE, not a closed standard, and the audit surfaces further runtime context we
leave to future expansion rather than fix as fields here: the inference backend
(vLLM vs.\ \texttt{hf} inverts the GSM8K \texttt{plain}/\texttt{cot} ordering in
our rerun, \S\ref{app:exp-grid}), the tokenizer version, and the dataset snapshot
(a task commit hash or Croissant checksum, which the Math-Verify case,
\S\ref{sec:math}, shows can change silently). These are the natural first targets
as the community adopts and grows the schema.

\paragraph{Robustness of the judge-model effect.} To verify the effect is not a
single-task or small-panel artefact, we replicated the experiment with eight
judge families, adding DeepSeek, Mistral, Qwen, and Amazon to the original
four, and analysed it per MT-Bench task category
(Appendix~\ref{app:exp-judge}). The effect strengthens rather than washes out:

\section{Harness-Identification Audit Methodology}
\label{app:harness}

For each of the 10 audit papers (\S\ref{sec:harness-ann}), the ArXiv HTML
was retrieved from \texttt{arxiv.org/html/} and the pipeline's per-row
\texttt{eval\_library.name} value was verified against the source text by
hand. The audit operates at the (model, benchmark) row level rather than
the paper level, because a single paper can use a named harness for some
benchmarks and a separate pipeline (machine-translation suite, code
sandbox, LLM-as-judge, proof assistant) for others.

\paragraph{Strict-match rubric.} A row is \textsc{true} only if the
pipeline's harness label correctly names the tool the paper says was used
for that specific (model, benchmark) cell. The rubric accepts canonical
equivalents for the same library: ``eval-harness'', ``lm-evaluation-harness'',
``Language Model Evaluation Harness'', and ``LM-Evaluation Harness'' all
refer to EleutherAI's library and are treated as interchangeable. A
paper's distinctly-named fork (e.g., BLOOM's \emph{Prompted Language
Model Evaluation Harness}, the promptsource-extended fork the BLOOM
authors named, built, and released) is required as a verbatim match: the
pipeline must produce the fork's name, not the parent library's name,
because the two tools can produce different scores on the same input.

\paragraph{Sample composition.} The \emph{with-harness} pool has five
papers (BLOOM, Llemma, Sheared LLaMA, Aya 23, Nemotron-4 15B) covering
817 harness-call rows; the \emph{without-harness} pool has five (Code Llama, Mamba,
Reka, Jamba, a Llama-2-related survey paper) covering 869 abstention rows. The two
pools are disjoint from the score-verification sample
(Appendix~\ref{app:audit}). Per-row precision and abstention are reported
in \S\ref{sec:harness-ann}.

\paragraph{The \texttt{scoring\_mode} controlled vocabulary.}
\texttt{scoring\_mode} takes one of four values, defined by how the reported
score is produced. \textbf{log-likelihood}: the model assigns a probability to
each pre-specified answer option and the highest (length-normalised) token
log-probability is selected; no free text is generated. \textbf{generation}: the
model produces free text and the answer is extracted from it by a parser or
regex before scoring. \textbf{preference}: a judge (human or model) rates or
ranks outputs and the score is derived from those judgements (e.g., win rate,
Elo, or a 1--10 rubric rating). \textbf{execution}: the output is run against
test cases or a formal verifier and scored by the result (e.g., unit-test pass
rate, proof checking).

Multi-stage and hybrid pipelines are labelled by the stage that produces the
reported number, with the composite recorded in \texttt{benchmark\_variant}. A
pipeline that ranks candidates by log-likelihood and then generates a rationale
is \textbf{log-likelihood} if the ranked selection is scored and
\textbf{generation} if the generated text is scored. A preference judge applied
to a short answer extracted from free text is \textbf{preference} when the
rating is the score and \textbf{generation} when the extracted answer is matched
against a key. Chain-of-thought followed by a multiple-choice post-check is
labelled by the final selection mechanism. When two stages contribute to a
single merged score, the primary stage is recorded in \texttt{scoring\_mode} and
the secondary stage named in \texttt{benchmark\_variant}.

\subsection{Factorial Grid}
\label{app:exp-grid}

The framing experiment for \S\ref{sec:cases}. Four instruction-tuned
models (Qwen2.5-14B-Instruct, Qwen2.5-7B-Instruct, Llama-3.1-8B-Instruct,
Mistral-7B-Instruct-v0.3) were evaluated on three benchmarks (BBH, GSM8K,
MMLU) under three prompt formats (\texttt{plain} few-shot,
\texttt{instruct} system-prompt-formatted, \texttt{cot} chain-of-thought
few-shot; templates in Appendix~\ref{app:prompts}), two temperatures
(0.0, 0.7), and two n-shot counts per
benchmark: 0-shot plus 3-shot for BBH, 0-shot plus 5-shot for GSM8K and
MMLU. Three random seeds (42, 123, 7) were used per cell. MMLU was
reduced to temperature 0.0 with a single seed (42) due to
evaluation-server constraints. The analysis covers 306 successful evaluations:
144 BBH cells (4 models $\times$ 2 n-shots $\times$ 3 formats $\times$ 2
temperatures $\times$ 3 seeds), 144 GSM8K cells (same design), and 18
MMLU cells (3 models $\times$ 2 n-shots $\times$ 3 formats at temperature
0.0 with a single seed).

Inference was run with lm-evaluation-harness 0.4.11 and vLLM. GSM8K and
MMLU runs used a 200-problem subset (\texttt{limit=200}) for compute
budget; BBH used the full task suite. Variance attribution uses two
separate one-way ANOVAs on the prompt-format factor, computed per
benchmark on the 5-shot cells to avoid pooling across the unbalanced
GSM8K and MMLU designs. GSM8K contributes 72 cells (4 models $\times$ 3
formats $\times$ 2 temperatures $\times$ 3 seeds): prompt format yields
$F = 13.00$, $p = 1.6 \times 10^{-5}$, $\eta^2 \approx 27.4\%$, while
temperature contributes $\eta^2 \approx 0.25\%$ ($F = 0.18$, $p = 0.68$).
MMLU's reduced 9-cell design at 5-shot (3 models $\times$ 3 formats
$\times$ 1 temperature $\times$ 1 seed) is descriptively consistent
($\eta^2 \approx 24.5\%$) but underpowered ($F = 0.98$, $p = 0.43$); the
per-format means agree with the GSM8K pattern but cannot independently
confirm it. Per-format means for both benchmarks are reported in
Table~\ref{tab:anova-per-benchmark}.

To characterise the uncertainty in these point estimates under the
\texttt{limit=200} subsampling, we bootstrap each $\eta^2$ by resampling cells
with replacement within each prompt-format group ($10{,}000$ replicates). The
GSM8K format effect has a 95\% bootstrap interval of $[14.1\%, 44.8\%]$, which
excludes small effects and confirms the result is not an artefact of the
problem subset. The MMLU interval is $[3.3\%, 85.4\%]$: it spans nearly the
whole range, the bootstrap signature of the same underpowering the $F$-test
reports, and the reason we read MMLU as directional rather than confirmatory.

A direct full-benchmark rerun confirms the subset is representative. We re-ran the
Qwen2.5-7B-Instruct GSM8K \texttt{plain} and \texttt{cot} cells (5-shot, greedy) on
the full test set (1{,}319 problems) and at \texttt{limit=200}: scores agree to
within 1.3\,pp in both formats (\texttt{plain} 17.29 vs.\ 17.00; \texttt{cot} 58.23
vs.\ 59.50), so the 200-problem subset tracks the full set. This rerun used the
\texttt{hf} (transformers) backend, as vLLM was unavailable on the run environment
(a CUDA mismatch); its absolute scores and even the \texttt{plain}/\texttt{cot}
ordering differ from the vLLM grid, where the same cell scores \texttt{plain} 40.2
and \texttt{cot} 27.7. That cross-backend gap is itself an instance of our
thesis, the inference backend is an undocumented configuration choice that moves
scores, so the rerun validates subset representativeness within a backend, not the
vLLM absolute numbers. Script and raw records are released.

We attribute variance to the n-shot factor the same way, pooling each
benchmark's successful cells by shot count (0-shot vs.\ 5-shot;
Table~\ref{tab:anova-nshot}), and the two benchmarks behave oppositely in a
way that is itself diagnostic. On MMLU the n-shot effect is negligible:
pooled across models and formats, 0-shot scores 61.94 and 5-shot 59.34
(\(\eta^2 \approx 1.0\%\), \(F = 0.16\), \(p = 0.69\)). This corroborates
the HellaSwag analysis (\S\ref{sec:hellaswag}) with a controlled
measurement: on a log-likelihood-scored benchmark, varying n-shot moves the
score by at most a few points. On GSM8K the n-shot factor appears dominant
(\(\eta^2 \approx 65\%\) pooled, \(80\%\) within \texttt{plain}), but the
effect is not a capability gain: every 0-shot cell scores exactly 0.0,
because the instruction-tuned models without few-shot priming do not emit
the \texttt{\#\#\#\#} answer delimiter the GSM8K extractor requires, so the
parser records zero for every item. This is the same parser--format
coupling documented in Case Study~1 (\S\ref{sec:gsm8k}), here triggered by
shot count rather than prompt format: on a generation-and-parse benchmark
n-shot and scoring interact, whereas on a log-likelihood benchmark n-shot is
nearly inert.

\subsection{Prompt Templates}
\label{app:prompts}

The three prompt formats differ only in the system message applied through each
model's chat template; the few-shot body, five \texttt{Question:}/\texttt{Answer:}
exemplars followed by the target question, is identical across formats.
\texttt{plain} uses each model's default system prompt; \texttt{instruct} uses
``You are an expert problem solver. Answer each question carefully and
directly.''; and \texttt{cot} uses ``You are an expert problem solver. Before
answering, think step by step and show your reasoning. Then state the final
answer.'' The \texttt{instruct} and \texttt{cot} system messages are identical
across all four models; only \texttt{plain} varies, because it inherits the
model's own default. The exact rendered prompt for every (model, benchmark,
format) cell is released with the dataset, along with the canonical templates and
a worked example, so the prompt-format effect magnitudes can be reproduced
independently rather than only checked against a hash.

\subsection{Judge-Model Sensitivity}
\label{app:exp-judge}

Motivated by the TruthfulQA judge confound (\S\ref{sec:truthfulqa}) and the four
LLM-judge sources in the dataset (Chatbot Arena, AlpacaEval~2, MT-Bench,
WildBench), this experiment isolates the effect of the judge model. Five
instruction-tuned ``contestant'' models each generated one response to the 80
turn-1 MT-Bench questions \citep{zheng2023mtbench}; the identical responses were
then scored by four judge models from different providers (GPT-4o-mini,
Gemini-3.5-Flash, Llama-3.1-70B-Instruct, Claude-Haiku-4.5) using the canonical
MT-Bench single-answer 1--10 grading rubric at temperature~0. Because the
responses are held fixed, any variation in a contestant's mean score across
judges is attributable to the judge alone. Each cell aggregates 78--80 ratings,
except Gemini-3.5-Flash (48--63), which intermittently returned empty completions.

Table~\ref{tab:judge-sensitivity} reports the mean rating per
(contestant, judge). The judge-induced spread, the gap between a contestant's
highest and lowest judge mean, averages 1.08 points and reaches 1.35 points on
the 10-point scale. More consequentially, the judge choice reorders the
leaderboard: Ministral-8B is ranked first by GPT-4o-mini and Llama-3.1-70B but
last by Gemini-3.5-Flash. Pairwise Spearman rank correlations between judges
span the full usable range, from $+1.00$ (GPT-4o-mini vs.\ Llama-3.1-70B,
identical order) down to $-0.30$ (GPT-4o-mini vs.\ Gemini-3.5-Flash,
anti-correlated). The judge model is therefore not a calibration offset that
cancels in a comparison; it can invert which system appears better, so a
benchmark score produced by an LLM judge is uninterpretable without recording
the judge (\S\ref{sec:evalspec}).

\paragraph{Extended panel and per-task replication.} To test breadth, we repeated
the experiment with eight judge families (the original four plus DeepSeek-Chat,
Mistral-Large, Qwen2.5-72B-Instruct, and Amazon-Nova-Pro) over the same fixed
responses, and broke the result out by MT-Bench task category. The judge-induced
spread \emph{increases} with the wider panel, mean 1.66, max 1.80 on the
10-point scale (vs.\ 1.08/1.35 for four judges), because the added families rate
systematically more generously than Claude-Haiku and Gemini. Cross-judge Spearman
rank correlation over the eight judges spans $+1.00$ to $-0.10$ (mean $+0.61$,
28 pairs): the ranking stays unstable. The effect is present in all eight task
categories, with mean per-category spreads of 2.9 (coding), 2.5 (extraction),
2.4 (math), 2.3 (humanities), 2.1 (roleplay), 2.0 (stem), 1.9 (reasoning), and
1.5 (writing), largest on the structured, verifiable tasks. The judge-model
effect is therefore neither a single-task nor a small-panel artefact.
