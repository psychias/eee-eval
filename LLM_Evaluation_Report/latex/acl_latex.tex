\begin{abstract}
Leaderboard scores for the same model on the same benchmark routinely disagree by
tens of points, yet the public record rarely says why. We assemble 46{,}559
evaluation records from 12 public sources (7{,}398 models, 1{,}954 benchmarks) into
one schema and audit what configuration information survives. In the
28{,}755-record, 10-source leaderboard subset, the fields that would explain
divergence are absent: prompt template and temperature have zero valid coverage,
and no leaderboard API we examined exposes the harness. Three case studies trace how this
missing metadata makes cross-source gaps uninterpretable, isolating three
mechanisms: a benchmark implemented differently across harnesses (scoring mode,
parsing); multiple legitimate measurements under one name (n-shot, language scope,
judge); and apparent independent agreement that is one pipeline reported twice. A controlled factorial experiment quantifies the effects: prompt format
alone drives 27\% of GSM8K variance, temperature under 1\%. We adapt the open EEE
schema into EvalSpec, requiring the fields whose absence breaks comparison, and
release it with the dataset so future evaluations report extractable, comparable
configurations.
\end{abstract}

Open LLM Leaderboard v2 (OLv2) reports Gemma-7B's Big-Bench Hard (BBH) score as
21.12; the Jamba, RecurrentGemma, and MAmmoTH2 papers, among others, report BBH
between 55 and 60 for the same model, a gap over 35 points. Neither side
fabricates: each reports the score its pipeline produced. The missing procedure:
OLv2 scores BBH 3-shot by multiple-choice log-likelihood (\texttt{acc\_norm}),
whereas the papers use the original 3-shot chain-of-thought protocol. These are
not the same measurement, and a benchmark name does not make them so. The pattern
recurs for Gemma-2-9B (\S\ref{sec:sealion}), where the metadata distinguishing
the two protocols is stripped from every record before the scores meet.

This is the rule, not the exception: results pass through a chain of hands, a
model author runs an internal sweep, a leaderboard re-evaluates the checkpoint,
an aggregator scrapes it, a downstream paper cites the aggregator, and at each
stage how the score was produced is lost or quietly reinterpreted, until two
scores meeting on a comparison table share nothing but a benchmark name. We therefore assemble 46{,}559 records from 12 sources (7{,}398
models, 1{,}954 benchmarks) and ask what configuration survives in the 10-source
28{,}755-record leaderboard subset. The fields that most determine a score
(harness, scoring mode, prompt template, n-shot) are the ones it records least:
prompt template has zero coverage, and no leaderboard API we examined exposes the
harness. Temperature is also absent, but a factorial experiment
(\S\ref{sec:cases}) shows it drives under 1\% of variance, so its zero coverage
costs little; the high-impact fields do the damage. We then diagnose cases where
one model received sharply different scores on one benchmark.

The case studies are the contribution; the pipeline is the instrument that found
them. Each isolates a mechanism making scores incomparable without either source
erring: implementation choices the benchmark leaves underspecified, multiple
legitimate measurements under one name, and apparent independent evidence sharing
one pipeline. This is an audit-grounded position paper: dataset as
instrument, mechanisms as evidence, EvalSpec as remedy.

\textbf{Contributions.}
\begin{itemize}
    \item A cross-source audit of metadata coverage in the public evaluation ecosystem.
    \item Three case studies of cross-source score divergence, diagnosed end-to-end.
    \item EvalSpec, an adaptation of the EEE schema requiring the fields whose
      absence the audit shows to break comparison.
    \item Public release of the dataset (46{,}559 records) and the EvalSpec schema
      under CC-BY-4.0, built on the EvalEval EEE schema
      \citep{evaleval2026everyevalever} so future evaluation papers report
      extractable scores and the community can adopt and extend it.
\end{itemize}

Benchmark scores are sensitive to implementation choices the public record rarely
exposes: \citet{alzahrani2024} report MMLU gaps up to fifteen points from harness
choice alone; \citet{biderman2024} extend this to prompt format, tokenisation, and
generation configuration; \citet{singh2025} document Chatbot Arena instability under
different aliases; and data contamination \citep{sainz2023} is a parallel threat
whose detection also needs richer per-run records. These show \emph{that} scores
vary with protocol; we trace how that variation enters the cross-source record and
which absences produce which gaps.

A separate line proposes structured documentation. Model Cards \citep{mitchell2019}
and Datasheets \citep{gebru2021} set the norm for models and data; three concurrent
2025 proposals, BenchmarkCards \citep{sokol2025}, EvalCards \citep{dhar2025}, and
Eval Factsheets \citep{bordes2025}, extend it to evaluation. All are prescriptive
prose; EvalSpec (\S\ref{sec:evalspec}) differs on the two axes that decide whether a
specification changes practice: it is \emph{machine-validated} (records checked by
SHACL constraints, not prose) and \emph{audit-grounded} (fields chosen because their
absence demonstrably breaks comparisons, \S\ref{sec:cases}). Holistic harnesses like HELM \citep{liang2023helm} record rich
per-run metadata (adapter method, decoding parameters, prompt construction), but
only for their own runs and without a portable cross-source \texttt{scoring\_mode}
label; EvalSpec instead targets cross-source interchange. General reproducibility checklists \citep{pineau2021reproducibility} and
benchmark-lifecycle checklists such as HOW2BENCH \citep{cao2025how2bench} are
hand-filled prose relying on manual adherence; EvalSpec instead makes conformance
machine-checkable, e.g.\ a SHACL shape requiring \texttt{judge\_model} whenever
\texttt{scoring\_mode} is \texttt{preference} mechanically rejects an LLM-judge score
that omits the judge (Appendix~\ref{sec:truthfulqa}, Appendix~\ref{app:exp-judge}),
shifting the guarantee from voluntary compliance to automatic validation. Concern
with evaluation reproducibility predates the LLM era: \citet{gundersen2018reproducibility}
surveyed reproducibility across AI and \citet{belz2021systematic} systematically
reviewed NLP reproduction attempts, both tracing failures to underreported
experimental settings; EvalSpec carries that lineage to the configuration fields
that break present-day cross-source comparison. A complementary line adds error bars and multi-run aggregation to quantify a single
producer's sampling and seed variance \citep{miller2024errorbars}; this composes with
EvalSpec, which makes the run \emph{configuration} comparable across sources and whose
Recommended tier carries the random seed such aggregation needs. EvalSpec sits on
existing infrastructure, adopting EEE as its interchange substrate. It composes with Croissant
\citep{akhtar2024croissant} along an orthogonal axis: Croissant and its task-level
extension \citep{croissanttasks2026} pin the \emph{artifact} (which files, which
record structure, a per-file \texttt{sha256}) and \emph{what} a benchmark measures,
explicitly leaving execution to other tools; EvalSpec pins the \emph{procedure},
the harness, scoring mode, prompt, shots, decoding, and judge that Croissant lists
among its non-goals and where same-model, same-dataset scores diverge. A Croissant
checksum is exactly the dataset-snapshot field in EvalSpec's Full tier, so a record
can populate it by reference rather than re-encode it.

\paragraph{Operational evaluation systems.} A parallel line builds \emph{systems}
around evaluation rather than specifications for it. Evaluation Cards
\citep{ghosh2026evalcards} compose benchmark, run, and model metadata into a
monitoring layer that derives reproducibility, provenance, and comparability signals
at scale; HRET \citep{lee2025hret} is a registry-based execution toolkit
standardising how evaluations are \emph{run}, narrowing $\sim$10-point
cross-institution gaps on Korean benchmarks; and DEP \citep{peng2026dep} keeps
benchmark data server-side to prevent leakage. Platforms differ in how much run metadata they expose: OpenCompass
\citep{opencompass2023} dumps its resolved config but surfaces few-shot count, prompt
template, and temperature only as ad~hoc script parameters, with no per-score field or
scoring-mode label, while LightEval \citep{lighteval} records richer provenance
(harness commit, model SHA, per-task version, prompt hashes) yet leaves decoding
parameters and the generation-vs-log-likelihood scoring mode implicit, exactly the
gap EvalSpec targets. Table~\ref{tab:crosswalk} (Appendix~\ref{app:crosswalk}) makes
this contrast concrete, mapping each EvalSpec Required field to whether HELM,
LightEval, and OpenCompass expose it as a first-class field, only implicitly, or not
at all.
These are complementary to a reporting specification: EvalSpec neither runs (HRET),
hosts (DEP), nor monitors (Evaluation Cards) evaluations. It fixes the minimal
per-record fields whose absence provably breaks cross-source comparison
(\S\ref{sec:cases}), so a conformant record is exactly the input such systems
consume or emit, and whose comparability signals presuppose the fields EvalSpec
makes mandatory.


\subsection{The EEE Schema}

%% DRAFT --------------------------------------------------------------
% Our analysis builds on the Every Eval Ever (EEE) schema, a unified
% JSON format for storing evaluation records from heterogeneous sources.
% Each record captures one model's result on one benchmark from one
% source, organised into four blocks: \texttt{model\_info} describes
% the model under evaluation; \texttt{eval\_library} describes the
% harness used to produce the score; \texttt{source\_metadata} describes
% the source of the record and its provenance; and
% \texttt{evaluation\_results} contains the score itself along with
% per-run generation configuration. Table~\ref{tab:eee-fields} lists the
% fields most relevant to this paper.
%
% A unified schema is the right abstraction for cross-source comparison
% because the alternative --- comparing scores across sources whose
% formats and conventions differ --- requires implicit alignment that
% nobody verifies. The schema makes the alignment explicit and turns
% missing information from an invisible gap into a recordable absence:
% a field that no source populates is visibly empty in every record,
% rather than silently inferred away.
%% END DRAFT ----------------------------------------------------------

This paper builds on and extends the open Every Eval Ever (EEE) schema
released by the EvalEval Coalition
\citep{evaleval2026everyevalever}, which articulates the
cross-framework score-comparability problem we investigate (citing the
gap between HELM~\citep{liang2023helm} and EleutherAI's
lm-evaluation-harness~\citep{gao2024lmevalharness} on LLaMA~65B MMLU, 0.637
vs.\ 0.488).
EEE is a unified JSON format storing one model's result on one benchmark from one
source, with four objects: \texttt{model\_info} (model name, id, developer),
\texttt{eval\_library} (harness name and version), \texttt{source\_metadata}
(source, type, evaluator relationship), and \texttt{evaluation\_results} (metric and
score, with an optional \texttt{generation\_config} for temperature and prompt
template). A unified schema turns missing information into a recordable absence: a
field no source populates is empty in every record rather than silently inferred, and
those visibly-empty fields motivate this paper. We
adapt EvalSpec (\S\ref{sec:evalspec}) from EEE and release, under CC-BY-4.0, the
full dataset and schema together with the extraction and analysis code, the
controlled-experiment scripts, and the prompt templates and raw per-run outputs
behind every reported number, so each claim is reproducible end-to-end; the
collision, coverage, and audit scripts regenerate the corresponding tables from
the released records.

\subsection{How We Gathered the Data}
\label{sec:pipeline}

%% DRAFT --------------------------------------------------------------
% We ingest evaluation records from eleven public sources: eight
% leaderboards (Open LLM Leaderboard v2, AlpacaEval 2, Chatbot Arena,
% BigCodeBench, EvalPlus, BFCL, SWE-Bench, WildBench, MT-Bench), the
% HuggingFace model-card YAML model-index, and Papers With Code. Each
% source is handled by a dedicated converter that maps its native
% format onto the EEE schema; records that fail JSON-schema validation
% are dropped, and duplicates are deduplicated on the composite key
% \texttt{(model\_id, benchmark, source)}.
%
% The pipeline is not uniform in how much it trusts each source. We
% distinguish three levels.
%
% \paragraph{Deterministic.} Schema validation and ID normalisation are
% rule-based and do not depend on any heuristic. Model identifiers are
% lowercased; \texttt{-hf} suffixes and shot annotations are stripped;
% benchmark names are normalised to a canonical form. These operations
% are reversible and produce no false positives.
%
% \paragraph{Regex-based and fragile.} Papers With Code does not expose
% a structured API; results are scraped from HTML tables whose layout
% varies by paper. Score values, model identifiers, and benchmark names
% are extracted by regex. We treat this layer as the least reliable
% part of the pipeline and audit it explicitly in
% Section~\ref{sec:pwc-audit}.
%
% \paragraph{External knowledge.} Several sources do not expose the
% harness they use in their data, but the harness is known from
% platform documentation (for example, OLv2 uses lighteval; AlpacaEval
% uses alpaca\_eval). We record these inferred values in a separate
% \texttt{inferred\_harness} field rather than in
% \texttt{eval\_library.name}, so that self-reported and inferred
% values remain distinguishable downstream.
%
% Cross-source collisions are detected after normalisation: records are
% grouped by \texttt{(model\_id, benchmark)}, and every pair of records
% from distinct sources within a group is emitted as a collision pair
% with its score delta and metadata-match annotations. The full
% procedure is described in Appendix~\ref{app:collision}.
%
% We deliberately abstain from two operations that would otherwise be
% tempting. We do not use a language model to re-extract scores from
% paper PDFs or HTML, because doing so would introduce a second layer of
% errors that we could not separate from the errors already present in
% the sources. We do not manually correct individual records, because
% the audit's value depends on reporting what the public ecosystem
% actually contains, not what it would contain after curation.
%% END DRAFT ----------------------------------------------------------
The dataset draws on three source classes. Leaderboards are taken as
authoritative: each fetcher downloads at runtime, emitting a schema-conformant
record per model$\times$benchmark cell with n-shot and chain-of-thought from the
fixed protocol; OLv2 exposes only model ids, scores, and a submission date (no
harness, prompt template, scoring mode, or temperature). HuggingFace Model Cards
are parsed from the YAML \texttt{model-index}. Third, ArXiv extraction: an LLM
(Claude Haiku via OpenRouter) reads paper prose into the EEE schema for 100
papers, returning per-benchmark metadata (n-shot, temperature, prompt template,
chain-of-thought, harness) when explicitly stated; since it may hallucinate, we
treat these fields as unverified.

\section{Quantitative Analysis}
\label{sec:quant}

\subsection{Human Annotation of Automatic Score Extractions}
\label{sec:score-ann}

\paragraph{Score extraction precision and recall.}
We audited 2{,}027 extracted (model, benchmark, score) entries against 10 source
ArXiv papers (Table~\ref{tab:score-ann-app}, Appendix~\ref{app:audit}).
\emph{Precision}, extracted scores matching the paper, is \textbf{97.5\%}
(1{,}977/2{,}027); the 50 errors are systematic artefacts (base/chat variant
duplication, 33; a spurious HumanEval leading ``0'', 8; a Qwen1.5-32B-as-34B
mislabel, 5; duplicate Elo attribution, 3; one wrong pass@k, 1). \emph{Recall},
reported scores captured, is approximately \textbf{81\%} but variable (52--100\%
per paper): it captures headline tables but skips secondary ones and, in
table-heavy papers, whole comparison models. Neither check verifies surrounding
metadata; a third audit (\S\ref{sec:meta-ann}) covers the non-score protocol
fields. Separately, 16{,}374/17{,}228 (95.0\%) LLM-extracted ArXiv records carry a
non-null score, a structural presence check, not a correctness one.

\subsection{Human Annotation of Automatic Harness Identification}
\label{sec:harness-ann}
We assembled two balanced samples from the ArXiv source: five papers that name a
harness (\emph{with-harness}: BLOOM, Llemma, Sheared LLaMA, Aya 23, Nemotron-4
15B) and five that do not (\emph{without-harness}: Code Llama, Mamba, Reka, Jamba,
a Llama-2 survey), covering 817 and 869 harness-call rows. Each row's
\texttt{eval\_library.name} was verified against the source text under a strict
rubric (canonical equivalents accepted, a paper's distinctly-named fork required
verbatim; Appendix~\ref{app:harness}).

Per-row precision on the with-harness sample is 712/817 = 87.1\%: three papers
reach 100\% (BLOOM 436/436, with the \emph{Prompted Language Model Evaluation
Harness} fork correctly extracted, plus Sheared LLaMA and Aya 23), while two
expose a failure mode: when a harness is attributed to a broad group (``across
all aforementioned tasks'', Nemotron-4 15B, 6/96; ``for open access models'',
Llemma, 74/89), the LLM tags only the benchmarks named in the same sentence.
Abstention on the without-harness sample is 869/869 = 100\% (\texttt{unknown}
every row), and text search confirms none names a public harness for its own
evaluations.

\subsection{Precision of Metadata Beyond Scores}
\label{sec:meta-ann}
The score and harness audits leave the remaining protocol fields unchecked, so a
third audit used a six-paper sample disjoint from both (StarCoder~2,
DeepSeek-Coder-V2, Granite Code, Gemma~3, Qwen3, OpenELM), verifying the four
non-harness benchmark-level fields \texttt{n\_shot}, \texttt{temperature},
\texttt{prompt\_template}, and \texttt{decoding\_strategy}. As an independent
cross-extractor check, a second model re-read each paper's evaluation tables and
appendix, judging every non-null extracted value as matching, contradicting, or
\emph{unstated} (paper silent, so the value is a pipeline default, excluded from
precision). Across 229 distinct per-benchmark
tuples (631 non-null values), precision on values the paper actually states is
high: \texttt{n\_shot} 99.4\% (171/172), \texttt{temperature} 100\% (42/42),
\texttt{prompt\_template} 93.4\% (114/122), \texttt{decoding\_strategy} 98.8\%
(163/165), and 97.8\% overall (490/501). The eleven errors concentrate: eight
\texttt{chain-of-thought} \texttt{prompt\_template} labels on Gemma~3 benchmarks the
paper does not mark CoT, two Granite CRUXEval decoding labels (\texttt{greedy} vs.\
the paper's temperature~0.2), one Gemma~3 shot count (FLoRes-Indic 5 vs.\ 1). The more consequential finding is coverage-side: \textbf{21\%
(130/631) of extracted metadata values are unstated pipeline defaults}
(\texttt{prompt\_template=direct}, \texttt{decoding\_strategy=greedy},
\texttt{n\_shot=0} for completion benchmarks) the source paper never states.
Extraction of \emph{stated} metadata is therefore reliable, but apparent field
coverage overstates \emph{verifiable} coverage: \texttt{n\_shot} is both
high-precision and usually paper-stated, whereas \texttt{prompt\_template} and
\texttt{decoding\_strategy} are high-precision only \emph{when} the paper states
them. Since the reference judgments come from a second model, not a human, this is
an inter-extractor agreement rate, not precision against a gold standard; shared
failure modes make it an upper bound. The more robust finding is
the 21\% default-filling, which any reader can confirm against the cited papers;
released records flag inferred-versus-stated values so users can discount defaults.

The fields most responsible for divergence are either absent from the subset
(\texttt{prompt\_template} and \texttt{temperature} at 0\%) or present only
because the pipeline attaches \texttt{lm\_eval} to every OLv2 record from
documentation (\S\ref{sec:pipeline}). No leaderboard we examined returns harness

source data: the \texttt{lm\_eval} label is inferred from OLv2's documentation
\citep{openllmv2about}, and the scoring mode it runs (multiple-choice
log-likelihood on BBH, \S\ref{sec:bbh}) is not carried at all. Under a

figures largely measure one platform's API; ablating it sharpens the finding, as
the remaining nine sources expose nothing beyond the protocol-fixed n-shot count
(Table~\ref{tab:coverage-app}, final column; Limitations).

\paragraph{Scoring mode is unmeasurable.}
\texttt{scoring\_mode}, the field the case studies show most consequential, is
absent from the audit because no source records it discretely; it is implicit in
the harness configuration. Unlike harness identity it cannot even be
pipeline-attached, since one platform runs the same benchmark in either mode
(\S\ref{sec:bbh})---itself the argument for making it a first-class required field
(\S\ref{sec:evalspec}).

\section{Case Studies}
\label{sec:cases}

The case studies fall into three groups, one per mechanism by which scores
become incomparable across sources; Figure~\ref{fig:casestudies-unified} shows one
representative divergence for each. A controlled factorial experiment
quantifies the factors (four models $\times$ three benchmarks $\times$ three
prompt formats $\times$ two temperatures $\times$ two n-shot counts $\times$ three
seeds, MMLU reduced to a single temperature and seed; 312 evaluations), and
prompt-format sensitivity is assessed on five log-likelihood benchmarks
(Appendix~\ref{app:exp-grid}). Prompt format dominates on the generation benchmark
GSM8K, driving ${\approx}27\%$ of 5-shot variance ($F = 13.0$, $p < 0.001$)
through the format--parser coupling of \S\ref{sec:gsm8k}. On the five
log-likelihood benchmarks the effect is smaller but robust: a within-subject
(repeated-measures) ANOVA finds prompt format significant on four
(ARC-Challenge, WinoGrande, MMLU, OpenBookQA; all $p<0.01$) and null only on GPQA,
where the models sit at its chance floor, an order below the generation benchmark
(Appendix~\ref{app:exp-grid}).
Temperature contributes under 1\%, and the n-shot effect is benchmark-dependent
(negligible on MMLU, parser-bound on GSM8K). The case studies below show these
factors in the wild, each isolating one mechanism by which two separately published
scores under a shared name measure different things.

\subsection{Case Study 1: Undocumented Scoring Mode and Parsing}
\label{sec:protocol}

Here the harness makes choices the benchmark specification leaves
open, so different choices yield measurements incomparable on one scale even
when both are correct.

\paragraph{BBH: log-likelihood vs.\ chain-of-thought.}\label{sec:bbh}
BBH \citep{suzgun2023} specifies 3-shot chain-of-thought generation with the
answer extracted from free-form reasoning, the protocol ArXiv papers follow.
OLv2 instead runs BBH under its fork of the EleutherAI lm-evaluation-harness,
scoring 3-shot by normalised accuracy (\texttt{acc\_norm}): the model ranks the
fixed answer choices by log-likelihood, generating no reasoning
\citep{openllmv2about}. OLv2's API exposes no harness or scoring-mode field, so
both are known only from its documentation. The effect is visible in the data
(Table~\ref{tab:bbh-app}, Appendix~\ref{app:casetables}): Gemma-7B scores 21.12
on OLv2 against 55.10--59.60 in ArXiv papers,\footnote{The 59.60 figure is
reported under the surface label ``BigBench-Hard''; our normaliser keys on the
``BBH'' alias, so it is shown for completeness but held out of the automated
collision counts.} a gap over 35 points, and the same holds for Gemma-2-2B (11.76
vs.\ 40.80) and MAmmoTH2-7B-Plus (18.93 vs.\ 63.10). This is not a generic
scoring-mode effect: E2 (Appendix~\ref{app:exp-e2}) shows the
log-likelihood-vs-generation gap on MMLU is at most 0.21\,pp, two orders smaller,
so the BBH gap is specific to OLv2's multiple-choice log-likelihood meeting BBH's
CoT structure.

\paragraph{MATH Lvl 5: a silent answer-parser swap.} A third instance sits at the
dataset-version rather than scoring-mode layer: OLv2's February-2025 swap of the
MATH Level 5 answer parser (SymPy${\to}$Math-Verify) shifted scores by up to
${\approx}90$ points, yet no evaluation timestamp dates a record either side of
the transition---the same missing-metadata failure as BBH
(Appendix~\ref{sec:math}).

\paragraph{GSM8K: prompt format breaks the parser.}\label{sec:gsm8k}
The same parser sensitivity arises whenever a format-specific extractor meets a
prompt-shaped output. In the factorial grid, Qwen2.5-14B-Instruct on GSM8K
(5-shot, lm-evaluation-harness 0.4.11, temperature~0) scores 58.5\% (plain),
57.0\% (instruct), and 2.5\% (cot) (E1, Appendix~\ref{app:exp-e1};
Figure~\ref{fig:case1-parser}). The $\approx$56-point CoT collapse is parser
failure: the harness extracts the answer with the GSM8K delimiter
(\texttt{\#\#\#\#~\{answer\}}), which CoT prose omits, so the regex records zero
even when the reasoning is correct. As with Math-Verify, the score reflects the
parser's format assumptions, not capability, so CoT- and plain-prompted
GSM8K scores are incommensurable under one label.

\subsection{Case Study 2: One Name, Several Specifications}
\label{sec:onenametwo}

Unlike Case Study~1 (\S\ref{sec:protocol}), where one specification is implemented
differently by different harnesses, here several legitimate specifications coexist
under one benchmark name, so two equally-labelled scores can measure genuinely
different things. Each example states the gap, its two configurations, and
the missing field that would explain it.

\paragraph{TruthfulQA: n-shot and judge confounded.} Llama-2-Chat-7B appears at
57.04 (6-shot, GPT-3 judge) and 26.30 (0-shot, fine-tuned Llama-2-7B judge) under
one ``TruthfulQA'' label \citep{lin2022truthfulqa}, confounding shot count with
judge; holding responses fixed and varying only the judge, the judge
systematically changes ratings (Friedman
$\chi^2(7)=506.7$, $p<10^{-100}$, over 275 responses each scored by all eight
judges; Kendall's $W=0.26$), shifting means by up to 1.66/10 and reversing rankings
(cross-judge Spearman $+1.0$ to $-0.1$), so neither the missing \texttt{n\_shot}
nor \texttt{judge\_model} field is recoverable
(Appendices~\ref{sec:truthfulqa},~\ref{app:exp-judge}).

\paragraph{Belebele: n-shot and language scope confounded.}\label{sec:belebele}
Mistral-7B is recorded at 32.80 and 79.42, both ``Belebele''
\citep{bandarkar2023belebele}. The 32.80 is the Reka report
\citep{team2024reka} (0-shot, multilingual average over 150 variants); the 79.42
is Falcon2 \citep{malartic2024falcon2} (5-shot, English only). Falcon2's own
0-shot English score for Mistral-7B, 32.48, nearly matches Reka's 32.80---single
uncontrolled numbers, not a decomposition, but the near-match is
consistent with n-shot dominating: 0-shot$\to$5-shot on English spans nearly the
full 47-point gain ($32.48 \to 79.42$), language scope contributing little. Either
way the 46.6-point gap under one ``Belebele'' label confounds n-shot with language
scope, neither labelled.

\paragraph{HellaSwag: scoring mode and n-shot confounded.}\label{sec:hellaswag}
Gemma-7B is recorded at 49.80 and 81.20, both ``HellaSwag''
\citep{zellers2019hellaswag}. The 49.80 is the Phi-3 report
\citep{abdin2024phi3} (5-shot, generation-based, temperature~0); the 81.20 is
the Gemma report \citep{gemmateam2024gemma} (0-shot, log-likelihood over the
four continuations). The $\approx$31-point gap is too large for shot count
alone: on a log-likelihood benchmark n-shot moves scores by about a point (our
grid: MMLU 0-vs-5-shot differ 1.0\,pp, $\eta^2\approx0.1\%$,
Appendix~\ref{app:exp-grid}). The driver is scoring mode, since generating the
continuation is structurally harder than ranking pre-specified ones. Neither
record labels scoring mode or n-shot, so the gap is indistinguishable from a
capability difference (Appendix~\ref{app:hellaswag} gives an alternative rendering
of Figure~\ref{fig:casestudies-unified}).

\paragraph{When is a scoring-mode mismatch consequential? A diagnostic.}
A diagnostic
predicts, for a benchmark \emph{not} in our study, whether a
log-likelihood-vs-generation mismatch can move the score: it can, to the degree the
benchmark is high-risk on any of three protocol axes:
\begin{itemize}
\item \textbf{Answer-extraction dependence:} does scoring parse/normalise generated
text (high-risk) or rank fixed options (low-risk)? Parser brittleness collapses
GSM8K when the \texttt{\#\#\#\#} delimiter is absent (\S\ref{sec:gsm8k}).
\item \textbf{Output-space constraint:} a small closed label set (low-risk) versus
open-ended generation (high-risk), which widens the space in which the modes diverge.
\item \textbf{Chain-of-thought interaction:} does the protocol elicit reasoning a
parser must reduce to a final answer (high-risk) or score the answer directly
(low-risk)? This is the BBH mechanism (\S\ref{sec:bbh}).
\end{itemize}
Pure multiple-choice log-likelihood benchmarks are low-risk on all three, so
prompt format moves scores by only a few points: MMLU differs by 0.21\,pp under
matched scoring (E2, Appendix~\ref{app:exp-e2}), and the five log-likelihood
benchmarks we evaluate (ARC-Challenge, WinoGrande, OpenBookQA, MMLU, GPQA;
Appendix~\ref{app:exp-grid}) show format spreads of a few points, an order below
the generation benchmarks, even where significant (four of the five, all but
GPQA). Benchmarks high-risk on one or more axes diverge by tens of points: GSM8K
(extraction + open output), BBH (extraction + CoT), HellaSwag (open continuation).
The prediction is therefore mechanical from the protocol, not the benchmark name,
and is what \texttt{scoring\_mode} plus the presence of a parser encodes---why
EvalSpec places \texttt{scoring\_mode} in the Required tier: it tells a reader
which axis a cross-source gap under a shared name could be hiding.
Table~\ref{tab:scoring-ref}
(Appendix~\ref{app:scoring-ref}) maps common benchmarks to their typical scoring
mode and the reporting variants that most often move their scores.

\subsection{Case Study 3: Shared Pipelines Fake Independence}
\label{sec:convergence}\label{sec:sealion}

Two sources reporting the same score to several decimals need not be independent
measurements; one may be the other re-reported. OLv2 reports Gemma-2-9B's BBH
score as 34.10, and the SEA-LION paper (\citealt{ng2025sealion};
arXiv:2504.05747) reports the same model at 34.10, an exact two-decimal
match, while listing Open LLM Leaderboard among its benchmark sources. Such a
match fits either direct importation of the OLv2 score or independent
re-evaluation on the identical harness, and the EEE record cannot
distinguish them; but our harness-version control (Appendix~\ref{app:exp-e3})
shows reruns vary by up to 2.81\,pp across seeds, so an exact two-decimal match is
more consistent with a re-import than an independent re-run under a different
seed. OLv2's exact, deterministic configuration could reproduce it, but
SEA-LION records none; either way the two records share a
pipeline origin. This is a plausibility argument from the decimal match and the
seed spread, not proof: the fields that would settle it directly---a
run or job ID, an \texttt{evaluation\_timestamp}, the \texttt{harness}, and a
\texttt{prompt\_template\_hash}---are absent from both records, leaving the match as
the only signal. Recording them, as EvalSpec requires, would replace the inference
with a check.

The Gemma 2 and Gemma 3 reports instead list 68.20, 69.00, and 69.40, using
chain-of-thought generation rather than OLv2's 3-shot multiple-choice log-likelihood
(the harness mismatch of \S\ref{sec:bbh} compounding here), which explains the
$\approx$35-point gap. All five sources are in Table~\ref{tab:sealion-app}
(Appendix~\ref{app:casetables}).

\subsection{The Misunderstanding Chain}

An evaluation result is the product of a long chain of decisions (harness,
version, prompt template, n-shot, temperature, scoring mode, answer
extractor), each known at evaluation time but almost all dropped before the
reader. The case studies locate the loss: at the leaderboard
(\S\ref{sec:protocol}), the benchmark label (\S\ref{sec:onenametwo}), and the
appearance of independent measurement (\S\ref{sec:convergence}). Both
alternatives to documentation fail where the need is greatest: re-extraction
cannot recover what the leaderboard subset never records
(Figure~\ref{fig:coverage}), and re-evaluation does not scale across thousands of
model--benchmark pairs. This leaves documentation, necessary if not sufficient.

\paragraph{From existence to prevalence.}\label{sec:prevalence} The case studies
establish that each mechanism \emph{occurs}; a corpus-wide pass shows how often the
precondition for catching one is present. Conservatively normalising model
and benchmark names across all 46{,}559 records (keeping base and instruct
checkpoints distinct) leaves 42{,}114 distinct model--benchmark cells, of which
only \textbf{267 (0.63\%)} are reported by two or more independent sources, a
direct measure of the fragmentation that makes cross-source verification rare.
Where that overlap occurs it usually disagrees: \textbf{185 of the 267 (69\%)}
differ by more than 1\,pp and \textbf{139 (52\%)} by more than 5\,pp (gaps
above 30\,pp are common, e.g.\ Gemma-2-9B BBH at 34.1 vs.\ 68.2 across OLv2 and
the model's own report), and unattributably so: \textbf{98\%}
lack the harness field in at least one colliding record, and scoring
mode is recorded in none (though corpus-wide, not special to
collisions (\S\ref{sec:discrepancies}), so the gap cannot be assigned to a cause).
Prevalence is thus bounded less by how often the mechanisms fire than by how
rarely two sources measure the same thing. Name normalisation is heuristic,
so 0.63\% is a lower bound; the released collision script reproduces the count.

\subsection{EvalSpec: Adapting EEE for Comparable Reporting}
\label{sec:evalspec}

%% DRAFT --------------------------------------------------------------
% EvalSpec is a machine-readable reporting specification for
% evaluation runs. It is designed to be the smallest set of fields that
% turns a score into an identifiable measurement: enough that two
% records meeting on the same benchmark can be compared without an
% intervening act of guesswork.
%
% Field selection follows from the audit. The Required tier
% (EvalSpec-R) contains the fields whose absence makes attribution
% impossible: model identifier, benchmark identifier, scoring mode
% (one of log-likelihood, generation, preference, execution), harness
% name and version, n-shot count, date, and random seed. The
% Recommended tier (EvalSpec-Rec) contains the fields whose absence

% APIs do not return them.

EvalSpec adapts the open EEE schema (\S\ref{sec:related}) to the gaps this audit
exposes: it requires the configuration fields whose absence the case studies show
to break cross-source comparison, so two records on the same benchmark compare
without guessing the procedure behind them. We release it with the
populated dataset as a starting point, not a finished standard.

Field selection follows from the case studies (\S\ref{sec:cases}):
\texttt{scoring\_mode} from the BBH and HellaSwag collapses
(\S\S\ref{sec:bbh},~\ref{sec:hellaswag}); \texttt{harness\_name} and
\texttt{harness\_version} from SEA-LION (\S\ref{sec:sealion}), where harness
identity separates independent measurement from a shared-pipeline artefact;
\texttt{n\_shot} and \texttt{benchmark\_variant} from TruthfulQA
(Appendix~\ref{sec:truthfulqa}), Belebele, and HellaSwag
(\S\S\ref{sec:belebele},~\ref{sec:hellaswag}), where shot count and
metric variant shift the regime unlabelled; \texttt{judge\_model} from TruthfulQA,
where varying only the judge moves means up to 1.35/10 and reorders rankings
(cross-judge correlations $+1.0$ to $-0.3$; Appendix~\ref{app:exp-judge}); and
\texttt{evaluation\_timestamp} from the Math-Verify swap (Appendix~\ref{sec:math}), which
changes scores silently under one label. Two Recommended fields follow the same
logic: \texttt{judge\_prompt\_hash} (the rating depends on the judge prompt and
rubric, not the model alone) and \texttt{answer\_parser\_version} (the Math-Verify parser
swap is invisible to \texttt{harness\_version}); hashed fields are canonicalised
before hashing to avoid spurious mismatches. The full set by tier is in
Table~\ref{tab:evalspec-fields-app}
(Appendix~\ref{app:evalspec}).

Instantiating these fields for the SEA-LION collision
(Table~\ref{tab:evalspec-worked}, Figure~\ref{fig:evalspec-json},
Appendix~\ref{app:evalspec}) shows two suffice: \texttt{scoring\_mode} splits the
34.10 log-likelihood pair from the 68--69 generation reports, and
\texttt{harness\_name} plus \texttt{evaluation\_timestamp} separate SEA-LION's
re-import from an independent re-run---all \texttt{unknown} in the actual records.

EvalSpec is encoded as a JSON-LD vocabulary (extending \texttt{schema.org},
compatible with Croissant) whose tiers SHACL shape constraints can mechanically
check; the prompt template is stored as a hash of its canonical string. None of
the required fields need new instrumentation; the values already exist at
evaluation time. The barrier is API exposure, not implementation cost.

\paragraph{For practitioners.}
\emph{Leaderboard operators} should expose \texttt{harness\_name},
\texttt{harness\_version}, \texttt{scoring\_mode}, and
\texttt{evaluation\_timestamp}, known at evaluation time, so a logging decision,
not an engineering project; SEA-LION (\S\ref{sec:sealion}) shows the cost.
\emph{Model developers}
should ship at least one EvalSpec-R record per reported benchmark, making scores
verifiable against later evaluations (E1, Appendix~\ref{app:exp-e1}:
58.5\% vs.\ 2.5\% from one unrecorded prompt format). \emph{Schema designers}
should treat \texttt{scoring\_mode} as a first-class controlled-vocabulary field
(\texttt{log-likelihood}, \texttt{generation}, \texttt{preference},
\texttt{execution}), since no combination of harness, n-shot, and timestamp
recovers the log-likelihood-vs.-generation boundary (BBH, \S\ref{sec:bbh}; E2,
Appendix~\ref{app:exp-e2} shows the converse: at most 0.21\,pp when scoring
mode alone varies).

\paragraph{Adoption.}
Because conformance is machine-checkable (SHACL), records validate automatically;
because the fields are uniform across sources, incomparable protocols stop being
silently averaged into ``SOTA'' comparisons and cross-source meta-analysis becomes
possible even under partial uptake. The cheapest path is producer-side:
developers who ship one EvalSpec-R record per benchmark make their scores
verifiable, pressuring aggregators and leaderboards to surface the same fields. To
lower even that cost we release a drop-in emission hook that turns an existing
lm-evaluation-harness run into EvalSpec-R records, auto-populating all
\textbf{8 of 8} Required fields, including \texttt{scoring\_mode} (read from the
task's output type) and the prompt-template hash that no leaderboard API exposes,
against the $\approx$0\% source-reported coverage of those fields
(\S\ref{sec:discrepancies}). The hook ports to HELM and Inspect by swapping
field accessors.

\paragraph{Interoperability with EEE.} EvalSpec is not a competing schema but a
compliance \emph{profile} over EEE: every EvalSpec field resolves to an existing
EEE path, so a conformant record is a valid EEE record with the
comparability-critical fields mandatory. The Required tier draws from EEE's
\texttt{model\_info}, \texttt{evaluation\_name}, and \texttt{generation\_config}
(harness, \texttt{scoring\_mode}, n-shot); the Recommended tier from
\texttt{metric\_config} (metric name, score normalisation, prompt-template hash)
and the remaining \texttt{generation\_config} arguments (temperature, decoding);
the Full tier from \texttt{source\_metadata} (inference backend, tokenizer, dataset
checksum). Because the profile is a tier annotation rather than a new container,
EEE's evolving \texttt{metric\_config} and its optional instance-level records
(per-item predictions) extend EvalSpec at no cost: a producer already emitting
instance-level EEE data satisfies the Full tier and enables item-level re-scoring,
while one emitting only the Required fields still yields comparable aggregate
scores. EvalSpec thus fixes a comparability \emph{floor} without capping the
reproducibility ceiling of richer EEE records, whose records are the natural unit
that operational systems (\S\ref{sec:related}) consume.

\paragraph{Provenance and reproducibility as first-class.} Two properties make the
above auditable rather than aspirational. First, \emph{each value carries its
evidence source}: EvalSpec adds a provenance tag separating source-reported values
(returned by the producer) from API-exposed, documentation-inferred (e.g.\ a
harness label attached from a leaderboard's docs), and LLM-extracted ones, so a
reader can tell measurement from inference, exactly the distinction the OLv2
harness label needs (\S\ref{sec:pipeline}); the released dataset already applies it
to the load-bearing inferred fields. Second, \emph{each headline number links to a
released artifact}: the dataset, extraction and analysis code, and the collision,
coverage, and audit scripts regenerate every reported table (\S\ref{sec:materials}).
With the EEE profile above and the crosswalk to
operational layers such as Evaluation Cards \citep{ghosh2026evalcards}, whose
signals consume precisely the fields EvalSpec makes mandatory, provenance and
reproducibility become structural properties of the record, letting a third party
audit a score and lowering the barrier to adoption.

Public evaluation records routinely report a score without the procedure that
produced it. Across 46{,}559 records from 12 sources, the fields most responsible
for score divergence (harness identity, scoring mode, prompt template) are largely
absent from the leaderboard subset, where prompt template and temperature reach
zero valid coverage and no API exposes the harness, and the cross-source overlap
enabling independent verification is rare and concentrated in one dominant source.
Three case studies turn ordinary score gaps into uninterpretable ones, and a
controlled factorial experiment confirms an undocumented prompt-format or
answer-parser choice moves a score by tens of points on the same model,
benchmark, and harness. Since re-evaluation does not scale and re-extraction cannot
recover what a source never recorded, documentation is the remaining strategy:
EvalSpec specifies the minimum fields to record, grounded in the audit and validated
on the case studies. The dataset, schema, and pipeline are released for the
community to extend.

\section*{Limitations}

\paragraph{Source concentration.} The leaderboard subset is 93\% Open LLM
Leaderboard v2 (26{,}790 of 28{,}755 records), so aggregate statistics largely
describe one dominant platform plus a sparse periphery. We report it separately
throughout and ablate OLv2 (Table~\ref{tab:coverage-app}): removing it, the
nine-source tail carries 0.0\% coverage on harness, prompt template, temperature,
and chain-of-thought, and only the protocol-fixed n-shot count (71.0\%) survives,
sharpening the headline rather than overturning it.

\paragraph{Single-extractor ArXiv pipeline.} The ArXiv source comes from one LLM
extractor (Claude Haiku). Three audits check it against the papers on scores
(\S\ref{sec:score-ann}), harness identity (\S\ref{sec:harness-ann}), and non-score
protocol fields (\S\ref{sec:meta-ann}); the last uses an independent second model
and surfaces the pipeline's default-filling (21\% of metadata values are unstated
defaults). These cover 26 papers, point estimates on a modest sample not
ecosystem-wide guarantees; we exclude ArXiv from the headline coverage and mark its
inferred metadata as such.

\paragraph{Existence vs.\ mechanism-level prevalence.} The case studies are
hand-selected for diagnosability, not sampled. The corpus-wide pass
(\S\ref{sec:prevalence}) shows overlap is rare (0.63\% of cells) and where it
exists divergence is the norm (69\% $>$1\,pp) and unattributable (harness missing
in 98\% of disagreements; scoring mode absent ecosystem-wide). It cannot attribute
each collision to a \emph{specific} mechanism, since the separating fields are the
missing ones; a mechanism-labelled census awaits enough records carrying
EvalSpec-Required fields.

\paragraph{Provenance inferences are plausibility arguments.} The sharper causal
reading of SEA-LION, an imported rather than independently re-run OLv2 score
(\S\ref{sec:sealion}), is plausible, not proven: the run identifiers, timestamps,
and harness fields that would confirm it are the very metadata absent from both
records, the thesis turned on itself. Recording them, as EvalSpec requires, would
settle it.

\paragraph{Statistical power and inference backend.} We estimate the format effect
on each log-likelihood benchmark with the replication unit its protocol admits
(Appendix~\ref{app:exp-grid}): seeds ($n{=}12$) for the random-few-shot
ARC-Challenge/WinoGrande/OpenBookQA, and models ($n{=}8$) for the seed-deterministic
MMLU/GPQA. A within-subject ANOVA (format repeated-measures, blocking on model)
finds it significant on four benchmarks (ARC-Challenge, WinoGrande, MMLU,
OpenBookQA; all $p<0.01$, Friedman-confirmed) and null only on GPQA, where models
sit at its chance floor; it is smaller than on generation-scored GSM8K but
conclusive. Addressing the \texttt{limit=200} and inference-backend (\texttt{hf}
vs.\ vLLM) confounds, the generalization arm scores all four models on a single
\texttt{hf} backend over full test sets (both \S\ref{app:exp-grid}): a GSM8K re-run
on \texttt{hf} reproduces the format--parser collapse (descriptive per-model
direction; pooled effect underpowered), so it is not a vLLM artefact, and the
\texttt{limit=200} subset is representative to within 1.3\,pp. The temperature
finding is not confined to GSM8K: a four-model, two-task generation panel over
temperatures 0.0--1.0 (\S\ref{app:exp-temp}) shows it explaining $2.2\%$ of GSM8K
accuracy variance and only $0.66\%$ of MT-Bench judged-quality variance (score
spread $0.05/10$), so its effect on \emph{aggregate scores} stays small even for
open-ended, judge-scored generation. The claim is scoped to scores, not outputs:
sampling still changes \emph{which} text is produced, so we make no claim for
diversity-sensitive uses (creativity, safety probing).

\paragraph{Pipeline-attached harness labels.} The 93\% harness coverage in the
leaderboard subset is inferred, attached by our pipeline from platform
documentation rather than returned by any API. Even when correct it is
insufficient: OLv2's docs name its lm-evaluation-harness fork but not the
\emph{scoring mode} it applies, which for BBH is 3-shot multiple-choice
log-likelihood (\texttt{acc\_norm}), not the chain-of-thought generation the
models' own reports use \citep{openllmv2about}. The effect is systematic: across
every pair where OLv2 and a model's own paper report the same benchmark, OLv2 is
lower in \textbf{37 of 42} BBH pairs (median \textbf{25.6\,pp}) and \textbf{19 of
24} MMLU-Pro pairs (median \textbf{8.0\,pp}). Since each pair is OLv2 vs.\ a
different paper's best-protocol number, this is suggestive rather than a clean
effect size and carries the papers' self-report choices, but is evidence that
missing scoring-mode metadata makes the divergence \emph{unattributable}; the
released dataset marks inferred fields and records scoring mode where known.

\paragraph{Extending the schema.} EvalSpec is an extensible adaptation of EEE, not
a closed standard. Its Full tier already reserves the runtime context the audit
surfaces: inference backend, tokenizer version, and dataset snapshot (a task commit
hash or Croissant checksum, which the Math-Verify case, Appendix~\ref{sec:math},
shows can change silently). Our backend control (Appendix~\ref{app:exp-grid}), where
switching vLLM to \texttt{hf} inverts GSM8K's \texttt{plain}/\texttt{cot} ordering,
argues for treating the inference backend and its version as a first-class parameter,
and for leaderboards pinning the backend, harness, and dataset snapshot behind every
published score in an archival contract. Standardizing these vocabularies and driving
their population are the natural next steps.

\paragraph{Robustness of the judge-model effect.} The effect is not a single-task,
single-dataset, or small-panel artefact. Replicated with eight judge families across
all MT-Bench task categories and on a second dataset (Vicuna-Bench), it strengthens
rather than washes out: the judge-induced spread rises to 1.66 (MT-Bench; 1.5--2.9
across categories) and 1.84 (Vicuna), and cross-judge Spearman falls as low as
$-0.4$, reinforcing \texttt{judge\_model} as a Required field (full statistics,
including the Friedman tests, in Appendix~\ref{app:exp-judge}).

\section{Harness-Identification Audit Methodology}
\label{app:harness}

For each of the 10 audit papers (\S\ref{sec:harness-ann}), the ArXiv HTML
was retrieved from \texttt{arxiv.org/html/} and the pipeline's per-row
\texttt{eval\_library.name} value was verified against the source text by
hand. The audit operates at the (model, benchmark) row level rather than
the paper level, because a single paper can use a named harness for some
benchmarks and a separate pipeline (machine-translation suite, code
sandbox, LLM-as-judge, proof assistant) for others.

\paragraph{Strict-match rubric.} A row is \textsc{true} only if the
pipeline's harness label correctly names the tool the paper says was used
for that specific (model, benchmark) cell. The rubric accepts canonical
equivalents for the same library: ``eval-harness'', ``lm-evaluation-harness'',
``Language Model Evaluation Harness'', and ``LM-Evaluation Harness'' all
refer to EleutherAI's library and are treated as interchangeable. A
paper's distinctly-named fork (e.g., BLOOM's \emph{Prompted Language
Model Evaluation Harness}, the promptsource-extended fork the BLOOM
authors named, built, and released) is required as a verbatim match: the
pipeline must produce the fork's name, not the parent library's name,
because the two tools can produce different scores on the same input.

\paragraph{Sample composition.} The \emph{with-harness} pool has five
papers (BLOOM, Llemma, Sheared LLaMA, Aya 23, Nemotron-4 15B) covering
817 harness-call rows; the \emph{without-harness} pool has five (Code Llama, Mamba,
Reka, Jamba, a Llama-2-related survey paper) covering 869 abstention rows. The two
pools are disjoint from the score-verification sample
(Appendix~\ref{app:audit}). Per-row precision and abstention are reported
in \S\ref{sec:harness-ann}.

\paragraph{The \texttt{scoring\_mode} controlled vocabulary.}
\texttt{scoring\_mode} takes one of four values, defined by how the reported
score is produced. \textbf{log-likelihood}: the model assigns a probability to
each pre-specified answer option and the highest (length-normalised) token
log-probability is selected; no free text is generated. \textbf{generation}: the
model produces free text and the answer is extracted from it by a parser or
regex before scoring. \textbf{preference}: a judge (human or model) rates or
ranks outputs and the score is derived from those judgements (e.g., win rate,
Elo, or a 1--10 rubric rating). \textbf{execution}: the output is run against
test cases or a formal verifier and scored by the result (e.g., unit-test pass
rate, proof checking).

Multi-stage and hybrid pipelines are labelled by the stage that produces the
reported number, with the composite recorded in \texttt{benchmark\_variant}. A
pipeline that ranks candidates by log-likelihood and then generates a rationale
is \textbf{log-likelihood} if the ranked selection is scored and
\textbf{generation} if the generated text is scored. A preference judge applied
to a short answer extracted from free text is \textbf{preference} when the
rating is the score and \textbf{generation} when the extracted answer is matched
against a key. Chain-of-thought followed by a multiple-choice post-check is
labelled by the final selection mechanism. When two stages contribute to a
single merged score, the primary stage is recorded in \texttt{scoring\_mode} and
the secondary stage named in \texttt{benchmark\_variant}.

\subsection{MATH Level 5: the Math-Verify answer-parser swap}
\label{sec:math}
This is the third sub-example of Case Study~1 (\S\ref{sec:protocol}), a
dataset-version rather than scoring-mode failure. OLv2 scored MATH Level 5
(1{,}324 problems, 5-shot) with a SymPy parser; in February 2025 HuggingFace
replaced it with Math-Verify and re-evaluated all models
\citep{kydlicek2025mathverify}. The old parser mishandled
\textbackslash{}boxed\{\} outputs, sets/matrices/intervals, and
numerical-equivalence (e.g.\ $1/3$ vs.\ $0.333\ldots$); the swap raised scores
by $+4.66$\,pp on average over 3{,}751 models ($+8.27$ Algebra, $+6.93$
Prealgebra, up to ${\approx}90$ points individually). OLv2 records a submission
date but no evaluation timestamp, so pre- and post-transition scores cannot be
told apart from the record, a model submitted in 2024 now carries a
post-transition score.

\subsection{TruthfulQA: n-shot and judge confounded}
\label{sec:truthfulqa}
A sub-example of Case Study~2 (\S\ref{sec:onenametwo}). Llama-2-Chat-7B is recorded
at 57.04 and 26.30, both labelled ``TruthfulQA'' \citep{lin2022truthfulqa}; both
use the generation-based metric (\% truthful and informative), not MC1/MC2. The
57.04 is from the Code Llama paper \citep{roziere2023codellama} (6-shot,
InstructGPT-format prompt, GPT-3 judge); the 26.30 figures use the T\"ulu suite
\citep{ivison2023camels}, e.g.\ the OLMo paper \citep{groeneveld2024olmo} (0-shot,
a fine-tuned Llama-2-7B judge). The 30-point gap therefore confounds shot count
(6 vs.\ 0) and judge (GPT-3 vs.\ a fine-tuned Llama-2-7B), and neither record
carries an \texttt{n\_shot} or judge field. A controlled experiment
(Appendix~\ref{app:exp-judge}) isolates the judge: over fixed responses, varying
only the judge shifts means by up to 1.35/10 and can reverse two systems' ranking,
so judge identity alone makes two ``TruthfulQA'' scores incomparable.

\subsection{Factorial Grid}
\label{app:exp-grid}

The framing experiment for \S\ref{sec:cases}. Four instruction-tuned
models (Qwen2.5-14B-Instruct, Qwen2.5-7B-Instruct, Llama-3.1-8B-Instruct,
Mistral-7B-Instruct-v0.3) were evaluated on three benchmarks (BBH, GSM8K,
MMLU) under three prompt formats (\texttt{plain} few-shot,
\texttt{instruct} system-prompt-formatted, \texttt{cot} chain-of-thought
few-shot; templates in Appendix~\ref{app:prompts}), two temperatures
(0.0, 0.7), and two n-shot counts (0-shot plus 3-shot for BBH, 0-shot plus
5-shot for GSM8K and MMLU), with three seeds (42, 123, 7) per cell. MMLU was
reduced to temperature 0.0 and seed 42 due to evaluation-server constraints.
The analysis covers 312 successful evaluations: 144 BBH cells (4 models
$\times$ 2 n-shots $\times$ 3 formats $\times$ 2 temperatures $\times$ 3
seeds), 144 GSM8K cells (same design), and 24 MMLU cells (the same minus the
temperature and seed factors).

Inference was run with lm-evaluation-harness 0.4.11 and vLLM; the MMLU cells
were additionally re-scored on the \texttt{hf} (transformers) backend to
recover runs that failed under vLLM, which is equivalent for log-likelihood
multiple-choice ranking (agreeing within 0.5\,pp on cells run both ways).
GSM8K and MMLU runs used a 200-problem subset (\texttt{limit=200}) for compute
budget; BBH used the full task suite. Variance attribution uses two
separate one-way ANOVAs on the prompt-format factor, computed per
benchmark on the 5-shot cells to avoid pooling across the unbalanced
GSM8K and MMLU designs. GSM8K contributes 72 cells (4 models $\times$ 3
formats $\times$ 2 temperatures $\times$ 3 seeds): prompt format yields
$F = 13.00$, $p = 1.6 \times 10^{-5}$, $\eta^2 \approx 27.4\%$, while
temperature contributes $\eta^2 \approx 0.25\%$ ($F = 0.18$, $p = 0.68$).
The prompt-format ANOVA on MMLU and the other log-likelihood benchmarks is
reported below (``Prompt-format sensitivity across log-likelihood benchmarks''),
each estimated across seeds or models as its protocol requires; per-format means
for the grid benchmarks are in Table~\ref{tab:anova-per-benchmark}.

To characterise uncertainty under \texttt{limit=200} subsampling, we bootstrap the
GSM8K $\eta^2$ by resampling cells with replacement within each prompt-format
group ($10{,}000$ replicates). Its 95\% bootstrap interval $[14.1\%, 44.8\%]$
excludes small effects, confirming the result is not an artefact of the problem
subset.

A direct full-benchmark rerun confirms the subset is representative. We re-ran the
Qwen2.5-7B-Instruct GSM8K \texttt{plain} and \texttt{cot} cells (5-shot, greedy) on
the full test set (1{,}319 problems) and at \texttt{limit=200}: scores agree to
within 1.3\,pp in both formats (\texttt{plain} 17.29 vs.\ 17.00; \texttt{cot} 58.23
vs.\ 59.50), so the 200-problem subset tracks the full set. This rerun used the
\texttt{hf} (transformers) backend, as vLLM was unavailable on the run environment
(a CUDA mismatch); its absolute scores and even the \texttt{plain}/\texttt{cot}
ordering differ from the vLLM grid, where the same cell scores \texttt{plain} 40.2
and \texttt{cot} 27.7. That cross-backend gap is itself an instance of our
thesis, the inference backend is an undocumented configuration choice that moves
scores, so the rerun validates subset representativeness within a backend, not the
vLLM absolute numbers. Script and raw records are released.

\paragraph{Prompt-format sensitivity across log-likelihood benchmarks.} We measure
the prompt-format effect on five log-likelihood benchmarks, estimating each with the
replication unit its protocol admits. ARC-Challenge, WinoGrande, and OpenBookQA draw
few-shot examples \emph{randomly}, so we vary the seed (42, 123, 7) across four
models for $n{=}12$ per format. MMLU and GPQA draw from a \emph{fixed} dev set and
are deterministic under greedy log-likelihood (varying the seed returns an identical
score), so we instead vary the \emph{model}, running eight instruction-tuned models
(1.5B--14B, four families) for $n{=}8$ per format. All runs use the \texttt{hf}
backend (MMLU on a 15\% stratified subset, ${\approx}2100$ items; the others
full-set).

Prompt format is a \emph{within-subject} factor, each model (or model--seed cell)
is scored under all three formats, so we test it with a repeated-measures ANOVA that
blocks on the subject; this removes the large between-model variance (a 1.5B and a
14B model differ by ${>}10$\,pp) that a one-way test would leave in the error term
and mask the effect. The format effect is then significant on four of the five
benchmarks, ARC-Challenge ($F(2,22)=23.4$, $p<10^{-4}$), WinoGrande
($F(2,22)=16.2$, $p<10^{-4}$), MMLU ($F(2,12)=10.2$, $p=0.003$), and OpenBookQA
($F(2,22)=5.7$, $p=0.01$), and the non-parametric Friedman test agrees ($p\le0.02$
for all four). It is null only on GPQA ($F(2,12)=1.98$, $p=0.18$), where the models
sit near GPQA's 25\% chance floor and format cannot move a near-random score. We
drop Phi-3.5 (its metric did not parse) and flag the Llama-3.1 mirror
(MMLU-depressed, GPQA at floor), but the conclusions are robust to excluding it. The
effect is therefore conclusive rather than suggestive, yet its \emph{absolute}
magnitude stays a few points, an order below generation-scored GSM8K's tens (\S\ref{sec:gsm8k}).
Prompt format thus matters on log-likelihood scoring too, just far less than where
scoring parses generated text (\S\ref{sec:hellaswag}). This arm runs entirely on
\texttt{hf}, removing the vLLM-vs-\texttt{hf} confound.

\paragraph{Backend control: is the GSM8K format effect a vLLM artefact?} To test
whether GSM8K's prompt-format effect is specific to the vLLM backend the grid uses
there, we re-scored GSM8K on the \texttt{hf} backend for all four models (single
seed, full test set, three formats). The descriptive per-model pattern replicates
the vLLM result and its mechanism: both Qwen models collapse under \texttt{cot}
(7B $37.0{\to}7.0$, 14B $38.2{\to}0.1$ from \texttt{plain} to \texttt{cot}) because
their chain-of-thought output drops the \texttt{\#\#\#\#} delimiter the parser
needs, exactly as on vLLM, while Mistral, whose \texttt{cot} output keeps the
delimiter, stays flat ($38.4/41.0/40.4$). The effect is thus mechanism-scoped, not
a generic ``format matters'' result: it appears precisely for the models whose
\texttt{cot} output omits the delimiter, the same format--parser coupling as Case
Study~1. The pooled prompt-format ANOVA over the three usable models
($\eta^2 \approx 37.8\%$, $F(2,6)=1.83$; Llama-3.1 excluded, as its NousResearch
mirror's chat template breaks the parser and floors all three formats near 2\%) is
underpowered and not significant, so it corroborates rather than confirms; but the
per-model direction matching vLLM on a second backend indicates the format effect
is not a vLLM artefact, disentangling backend from prompt format.

We attribute variance to the n-shot factor the same way, pooling each
benchmark's successful cells by shot count (0-shot vs.\ 5-shot;
Table~\ref{tab:anova-nshot}), and the two benchmarks behave oppositely in a
way that is itself diagnostic. On MMLU the n-shot effect is negligible:
pooled across models and formats, 0-shot scores 60.17 and 5-shot 61.16
(\(\eta^2 \approx 0.1\%\), \(F = 0.03\), \(p = 0.87\)). This corroborates
the HellaSwag analysis (\S\ref{sec:hellaswag}) with a controlled
measurement: on a log-likelihood-scored benchmark, varying n-shot moves the
score by at most a few points. On GSM8K the n-shot factor appears dominant
(\(\eta^2 \approx 65\%\) pooled, \(80\%\) within \texttt{plain}), but the
effect is not a capability gain: every 0-shot cell scores exactly 0.0,
because the instruction-tuned models without few-shot priming do not emit
the \texttt{\#\#\#\#} answer delimiter the GSM8K extractor requires, so the
parser records zero for every item. This is the same parser--format
coupling documented in Case Study~1 (\S\ref{sec:gsm8k}), here triggered by
shot count rather than prompt format: on a generation-and-parse benchmark
n-shot and scoring interact, whereas on a log-likelihood benchmark n-shot is
nearly inert.

\subsection{Prompt Templates}
\label{app:prompts}

The three prompt formats differ only in the system message applied through each
model's chat template; the few-shot body, five \texttt{Question:}/\texttt{Answer:}
exemplars followed by the target question, is identical across formats.
\texttt{plain} uses each model's default system prompt; \texttt{instruct} uses
``You are an expert problem solver. Answer each question carefully and
directly.''; and \texttt{cot} uses ``You are an expert problem solver. Before
answering, think step by step and show your reasoning. Then state the final
answer.'' The \texttt{instruct} and \texttt{cot} system messages are identical
across all four models; only \texttt{plain} varies, because it inherits the
model's own default. The exact rendered prompt for every (model, benchmark,
format) cell is released with the dataset, along with the canonical templates and
a worked example, so the prompt-format effect magnitudes can be reproduced
independently rather than only checked against a hash.

\subsection{Judge-Model Sensitivity}
\label{app:exp-judge}

Motivated by the TruthfulQA judge confound (\S\ref{sec:truthfulqa}) and the four
LLM-judge sources in the dataset (Chatbot Arena, AlpacaEval~2, MT-Bench,
WildBench), this experiment isolates the effect of the judge model. Five
instruction-tuned ``contestant'' models each generated one response to the 80
turn-1 MT-Bench questions \citep{zheng2023mtbench}; the identical responses were
then scored by four judge models from different providers (GPT-4o-mini,
Gemini-3.5-Flash, Llama-3.1-70B-Instruct, Claude-Haiku-4.5) using the canonical
MT-Bench single-answer 1--10 grading rubric at temperature~0. Because the
responses are held fixed, any variation in a contestant's mean score across
judges is attributable to the judge alone. Each cell aggregates 78--80 ratings,
except Gemini-3.5-Flash (48--63), which intermittently returned empty completions.

Table~\ref{tab:judge-sensitivity} reports the mean rating per
(contestant, judge). The judge-induced spread, the gap between a contestant's
highest and lowest judge mean, averages 1.08 points and reaches 1.35 points on
the 10-point scale. More consequentially, the judge choice reorders the
leaderboard: Ministral-8B is ranked first by GPT-4o-mini and Llama-3.1-70B but
last by Gemini-3.5-Flash. Pairwise Spearman rank correlations between judges
span the full usable range, from $+1.00$ (GPT-4o-mini vs.\ Llama-3.1-70B,
identical order) down to $-0.30$ (GPT-4o-mini vs.\ Gemini-3.5-Flash,
anti-correlated). The judge model is therefore not a calibration offset that
cancels in a comparison; it can invert which system appears better, so a
benchmark score produced by an LLM judge is uninterpretable without recording
the judge (\S\ref{sec:evalspec}).

\paragraph{Extended panel and per-task replication.} To test breadth, we repeated
the experiment with eight judge families (the original four plus DeepSeek-Chat,
Mistral-Large, Qwen2.5-72B-Instruct, and Amazon-Nova-Pro) over the same fixed
responses, and broke the result out by MT-Bench task category. The judge-induced
spread \emph{increases} with the wider panel, mean 1.66, max 1.80 on the
10-point scale (vs.\ 1.08/1.35 for four judges), because the added families rate
systematically more generously than Claude-Haiku and Gemini. Cross-judge Spearman
rank correlation over the eight judges spans $+1.00$ to $-0.10$ (mean $+0.61$,
28 pairs): the ranking stays unstable. The effect is present in all eight task
categories, with mean per-category spreads of 2.9 (coding), 2.5 (extraction),
2.4 (math), 2.3 (humanities), 2.1 (roleplay), 2.0 (stem), 1.9 (reasoning), and
1.5 (writing), largest on the structured, verifiable tasks. The judge-model
effect is therefore neither a single-task nor a small-panel artefact.

\paragraph{Second-dataset replication (Vicuna-Bench).} To rule out a dataset-specific
effect, we repeated the eight-judge study on Vicuna-Bench (80 single-turn questions)

judge-induced spread 1.84 (vs.\ 1.66); a Friedman test over the 389 fully-rated
responses rejects judge equivalence at $\chi^2(7)=908.5$ ($p<10^{-100}$, Kendall's
$W=0.33$); and cross-judge Spearman falls to $-0.40$.

\subsection{Temperature Panel}
\label{app:exp-temp}
To test whether the grid's ``temperature under 1\%'' result (GSM8K, greedy, parsed
short answers) generalises across generation tasks, we ran a panel via OpenRouter:
four models (Qwen2.5-7B, Qwen2.5-72B, Llama-3.1-8B, Ministral-8B) on GSM8K
(100-question subset, parsed) and MT-Bench (80 questions, scored 1--10 by a fixed
GPT-4o-mini judge), at temperatures $\{0.0, 0.7, 1.0\}$ with two samples each. A
one-way ANOVA over temperature finds $\eta^2 = 2.2\%$ on GSM8K accuracy (means
86.0/87.0/85.1) and $\eta^2 = 0.66\%$ on MT-Bench judged quality (means
8.63/8.61/8.58, spread $0.05/10$). Temperature thus moves \emph{aggregate scores}
little across the generation spectrum, from parsed short answers to open-ended
judged responses; it does change \emph{which} outputs are sampled, so this bounds
score sensitivity, not output diversity.
